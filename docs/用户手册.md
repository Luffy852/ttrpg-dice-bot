## 第一节 · 部署与更新（现行）

### 0. 先搞懂四件事（30 秒）

**① GitHub 存「源码」，Cloudflare 让它跑起来**

| 地方 | 干什么 |
|---|---|
| GitHub（`github.com`） | 存代码。你在这里上传 / 覆盖文件、点 Commit |
| Cloudflare（`dash.cloudflare.com`） | 真正让骰娘跑起来的地方：生成页面、跑后端、存每个房间的消息 |

两边用 **Connect to Git** 连起来：GitHub 一有改动，Cloudflare 自动重新部署（约 1～3 分钟）。

**② 平台是 Cloudflare「Workers」，不是 Pages**

入口、前端目录、房间数据库怎么建，全部由仓库最外层的 **`wrangler.toml`** 决定。
Cloudflare 里看到 "Workers & Pages" 这个菜单名不用困惑，我们用的是其中的 **Workers**。

**③ 前端页面不是你传上去的，是部署时「现生成」的** ★ 最容易误解的一条

`apps/web/index.html` 和 `apps/web/vendor/**` **不在 Git 里**。每次部署，Cloudflare 先跑
`node tools/build-web-shell.mjs`，从 `packages/engine/src/` 与 `packages/protocol/src/` 现生成它们。

- 所以**改了引擎 / 协议源码，不用再手工同步 vendor**（以前要成对传，现在不用了）；
- 也**永远不要**把生成物重新加回 Git；
- 从仓库拉下来的文件夹里**找不到 `index.html` 是正常的**，不是漏文件。

**④ 你以后最常做的不是「装」，而是「更新」**

第一次装只做一次（第 2 节）。之后所有改动都走 **「preview 先验证 → 再进 main」** 的路子，
具体节奏见 **第 3 节（本手册最重要的一节）**。
预览分支 **`preview/dice-bot` 长期保留**，每个包直接往这条分支传，**不用再创建新分支**。

### 1. 仓库里应该有什么

#### 认准这 5 个（在就对了，不用数文件个数）

| 路径 | 是什么 |
|---|---|
| `wrangler.toml` | **在仓库最外层**，和 `apps`、`packages` 并列（不是 `apps/worker/` 里面） |
| `apps/worker/src/index.js` | 后端入口 |
| `apps/worker/src/room.js` | 房间（Durable Object） |
| `packages/engine/src/domains.js` | 掷骰引擎源码 |
| `tools/build-web-shell.mjs` | 部署期生成前端页面的那个脚本 |

- `legacy/M2_骰娘单机可摸版.html` **必须保留**：它不会上线，却是生成前端页面和跑测试要读的输入，删了构建直接报错。
- `apps/web/index.html`、`apps/web/vendor/**` **查不到是对的**（见 0.③）。

#### ★ 点开头的文件：拖目录会静默漏掉

`.gitignore`（仓库根）和 `apps/web/.assetsignore`（前端目录根）都是**点开头**的文件，
浏览器的文件选择器默认不显示它们 —— **拖文件夹上传会漏，而且不报错**。

网页端一律走 **`Add file → Create new file`**，**手打含前导点的完整文件名**，
然后在最近一次 commit 的变更列表里**核对它确实在**。

> `.assetsignore` 控制「哪些文件会被上传成静态资源」；网页端的「构建监视路径」只控制
> 「哪些改动会触发一次构建」—— 这是**两层**，别混。
> Build 日志里的 `Read N files` 不能拿来判通过，要看**真实响应**：
> 比如打开 `/package.json` 应该返回首页，而不是一坨 JSON 包元数据。

#### 绝对不能出现在仓库里

`node_modules/`（本地测试装的一大堆库，几十 MB）、`.dev.vars`（真实密钥）、
`.DS_Store`、任何 `.zip` / `.rar`、别的项目文件。
`git` 会挡住一部分，但**网页端拖传是手动勾选，它拦不到已选中的项**，自己看一眼最保险。

### 2. 一次性配置（只在第一次装时做）

#### 第 1 步 · 连 Git

Cloudflare 左侧 **Workers & Pages** → **Create** → **Connect to Git**
（可能写作 "Import a repository" / "Connect to GitHub"，同一个意思）
→ 第一次授权 GitHub，选 **Only select repositories**，只勾 `ttrpg-dice-bot` → **Begin setup**。

#### 第 2 步 · 填配置（照抄）

| 框的名字 | 填什么 |
|---|---|
| Project name / 项目名称 | `ttrpg-dice-bot` |
| Production branch / 生产分支 | `main` |
| **Build command / 构建命令** | **`node tools/build-web-shell.mjs`** ★ 必须填 |
| Deploy command / 部署命令 | **留空**（用默认 `npx wrangler deploy`） |
| Preview command / 预览命令 | **留空**（用默认 `npx wrangler preview`） |
| Root directory / 根目录 | **留空** |

> 📌 2026-11-03 首次装机时，这几个框**曾经全部留空**；T2 起改成上面这样。
> 看到旧记录写「构建命令留空」不用困惑，那是当时的做法，**现在以本表为准**。

然后 **Save and Deploy**，等 1～3 分钟看绿色 **Success**。
正式地址是 **`https://dicebot.finewinginnovation.cn`**（自定义域名）；
`*.workers.dev` 只是首次部署时 Cloudflare 给的默认地址，不用记。

#### 第 3 步 · 设密钥（PIN_SECRET）

**Workers & Pages → `ttrpg-dice-bot` → Settings → Variables and Secrets → Add**

- **Type**：选 **Secret（机密）**，不要选 Text
- **Variable name**：`PIN_SECRET`（全大写、中间下划线，一模一样）
- **Value**：一串长一点的乱字符，自己记在别处（设完网页上就不再显示）
- 点 **Deploy / Save**。列表里出现一行 `PIN_SECRET`、值是 `•••••` 就对了。

★ 三条硬规矩：
- **只能**在 Cloudflare 网页端设，**绝不写进仓库任何文件**；
- **生产与每个 Preview 各有独立的密钥槽位**（预览不继承生产）—— 新开预览实例要单独补一次；
- **不要轮换**：换了会让所有带 PIN 的房间**永久进不去**。

#### 第 4 步 · 打开预览能力

开启「非生产分支构建 / 预览构建」。`wrangler.toml` **末尾**的 `[previews]` 块必须存在，
且里面声明了 `ROOM` 这个 Durable Object 绑定（代码通过 `env.ROOM` 读它）——
**空块会让预览实例建房直接 500**。

> 这个块**只影响预览**；`wrangler.toml` 的**顶级配置一条都不能动**
> （`name` / `main` / `compatibility_date` / `durable_objects` / `migrations` / `assets` / `observability`）。

#### 第 5 步 · 报错了怎么办

若报 **`assets-upload-session` / code 10013**：**不是代码问题**，是 Cloudflare 自己的上传服务在抽风。
**什么都不要改，直接 Retry build**，多数一次就过；旧版本继续在线上跑，不会中断。

⚠️ **千万别用「换个新 Worker 名字」来绕**：房间数据在 Durable Object 里，
DO 命名空间跟着 Worker 脚本名走 —— 改一次名字 = 全新命名空间 = **所有房间数据消失**。

### 3. ★ 以后的更新工作方式（本手册最重要的一节）

一句话：**每个更新包先上 preview 验，验过才进 `main`**。但有两种节奏，第二种是咱们新定的「开口」。

#### 每次你会拿到什么

- 一个 **更新包 zip**：只含这次改动 / 新增的文件，按仓库目录结构放好，覆盖同名即可；
- 一份 **简版操作指引**：只列大动作 + 本步独有的验收项；
- **有删除项才**另给一份「删除清单」（没有就不给）。

> 拖传只能**新增或覆盖同名文件，永远不会删除**。要删得在 GitHub 网页端点进那个文件 →
> 右上角**垃圾桶** → Delete file → Commit changes，全是点击。

---

#### 节奏 A · 标准（一步一合并）

1. 在**长期保留的 `preview/dice-bot`** 分支用 `Upload files` 覆盖 / 新增包内文件 → **一次 Commit**（不用新建分支）
   （同批文件一次传完，别拆成两个 commit，自动部署只取其一）
2. 等 Cloudflare 部署完，在**预览 URL** 按指引验收
3. 通过后把 preview **合并到 `main`** → **生产复验**
4. 下一轮我拉新的 `main` 做「向后比对 + 评估」，再出下一步的包

适合：大改动、跨阶段步骤、**T7 这类回归封版**。

---

#### 节奏 B · 开口 ★（细分阶段内攒几个小更新，最后一次性同步）

**什么时候能用**（三条都要满足，且**由你明确说一句**才开启，我不会自己改节奏）：

| 条件 | 说明 |
|---|---|
| ① 同一个细分阶段 | 几个包都是**小改动、互相关联**，不是跨阶段的大改 |
| ② **起点拉齐** | 开始时 `preview/dice-bot` 与 `main` **逐字节一致**；若 preview 已经领先，先把上一阶段收口合并、等两分支再次一致，才开启下一轮 |
| ③ 你明确指令 | 例如「这几步先累积在 preview，最后一次性合并」 |

**怎么做**：

1. 第一个包上 **preview** → 预览验过 → **不合并 `main`**
2. 第二、第三个包继续上**同一个 preview 分支**，**每包仍各自验一次可用性**
3. 等这整个小阶段做完，**一次性把 preview 整合到 `main`**
4. 合并后两分支应**逐字节一致**，再做一次生产复验

**为什么更省**：起点一致、几个小改动互相关联，就不必每包都跑一趟
「合并 → 拉新 `main` → 再比对」。这就是咱们说的 **「小步更新，打包同步」** ——
省的是来回合并的开销，**不是省验证**。

**实际例子**：T6 家族（T6 / T6a / T6b）三个包就是这么走的：三包累积在 preview 逐一验过，
最后一次性整合 `main`，历史房间命令测试通过。

**边界（别扩大用）**：

- 每包**仍然要单独验**，攒着不等于可以跳过验证；
- 开发侧每轮仍要做 **向后比对（适用性）+ 评估优化环节**，只是比对的锚点从 `main` 换成 preview；
  另外会在「干净 `main` + 已出各包依次叠加」上预演一次最终终态，确认一次性合并后自完备；
- **大改动 / 封版步骤不走这个口子**（如 T7 回归封版），仍按节奏 A；
- 合并后的**生产复验一次都不能少**。

---

#### 合并前必做的 4 项影响评估（两种节奏都一样）

| 查什么 | 为什么 |
|---|---|
| `wrangler.toml` **顶级配置**与迁移 tag 原样 | 改一次 = 另起空 DO 命名空间 = 全部房间失联 |
| 房间定位仍是 `env.ROOM.idFromName(code)` | 房间号不变、**已有房间数据不动** |
| 幂等 DDL：`ALTER TABLE … ADD COLUMN notified_clean` 只补列、不改已有行 | 这是唯一会碰旧库的动作；★ 索引必须在「建表 → 补列」**之后单独建**（009950 事故：混在一起老房间会 HTTP 500 / ws 1006） |
| `PIN_SECRET` 没轮换、`preview/dice-bot` 长期保留 | 带 PIN 的房间还能进；预览通道下次接着用 |

**已知副作用**：部署瞬间**活跃 WebSocket 会断开并自动重连** → **挑低活跃时段合并**。

**生产复验必含**：用**真实旧房间号进房**（如 593353），验历史消息、成员昵称、规则、战报条数；
带 PIN 的房间用**原 PIN** 能进。其余按**第二节**从 A 组往下勾。

### 4. 常见疑问

**Q：为什么仓库里找不到 `index.html`？**
A：生成物不入库，部署期由 Build command 现生成（见 0.③）。找不到是对的，别去补传一个。

**Q：改了引擎 / 协议源码，要不要手工同步 `vendor/`？**
A：**不用**。部署期 `node tools/build-web-shell.mjs` 会重建；本地跑全量前 `check:all` 也会先跑它。

**Q：为什么有个 `preview/dice-bot` 分支一直不删？**
A：它是**长期保留的验证通道**，每次更新包都直接往这条分支传、验过才合并到 `main`，**不用再新建分支**；删了下次得重建预览实例、还要重设密钥槽位。

**Q：更新包里为什么没有全部文件？**
A：只含改动 / 新增，同名覆盖即可。**有删除项才另给清单**，照着点垃圾桶删。

**Q：点开头的文件怎么传？**
A：`Add file → Create new file`，手打含前导点的完整文件名，再到 commit 变更列表里核对（见第 1 节）。

**Q：怎么确认 `.assetsignore` 真的生效？**
A：看真实响应 —— 打开 `/package.json` 返回的是**首页**，不是 JSON；别看 Build 日志里的文件数。

**Q：预览房间的数据会串到生产吗？**
A：不会。每个 Preview 有**独立的 DO namespace**，与生产完全隔离；生产旧房间号在预览里访问不到，反之亦然。

**Q：我看不懂代码，会不会传错？**
A：不会。你只要保证「包内文件按目录放对、点文件手打创建、同批一次 Commit」就行，代码本身不用动一个字。

### 5. 绝对不能做的事

- ❌ 把 `apps/web/index.html` / `apps/web/vendor/**` **重新加回 Git**
- ❌ 改 **Worker 名字 / DO 绑定名 / 迁移 tag** 来绕过报错
- ❌ **轮换 `PIN_SECRET`**
- ❌ 删掉或另建预览分支（**`preview/dice-bot` 长期保留**）
- ❌ 在 Cloudflare 上手动改代码（会被 GitHub 覆盖）
- ❌ 用 **404 判生成物**：`/vendor/*` 返回首页 200 是 SPA 兜底的正常行为，别当成「文件还在」或「部署失败」

### 出问题时

| 现象 | 最可能的原因 | 怎么办 |
|---|---|---|
| 页面空白 / 按钮没反应 | 生成物没重建，或包传漏了 | 看 Build 日志有没有跑 `build-web-shell.mjs`；必要时 Retry build |
| Application error / 1101 | `PIN_SECRET` 没设 | 按第 2 节第 3 步补设（**预览实例要单独补**）后重新部署 |
| 预览里建房 500，生产正常 | `[previews]` 块缺 `ROOM` 绑定 | 核对 `wrangler.toml` 末尾；**顶级配置一条别动** |
| `assets-upload-session` / 10013 | Cloudflare 上传服务故障 | 直接 **Retry build**，什么都不改 |
| 提示 "Durable Object migration required" | 迁移 tag 被改 | 截图发我，**不要**自己改 `wrangler.toml` |
| 打不开 / 404 | 还在部署，或部署失败 | 回 Cloudflare 看部署状态是不是绿 |

**回滚**：Cloudflare → 你的 Worker → **Deployments** → 找到上一个成功的 → **Rollback**。房间数据不会丢。

### 术语表（看到不懂的词来查）

| 词 | 人话 |
|---|---|
| Worker | 跑在 Cloudflare 上的后端小程序 |
| Durable Object（DO） | 每个房间一个的「小数据库」，存这个房间的消息 |
| SQLite | 数据库的一种，就当是「存消息的表格」 |
| `wrangler.toml` | 告诉 Cloudflare 怎么部署的配置文件（在仓库最外层） |
| Build command | 部署前先跑的一行命令；本项目用来**现生成前端页面** |
| 生成物 | `index.html` 与 `vendor/**`，部署期现做、**不进 Git** |
| Secret / `PIN_SECRET` | 给房间口令做签名的密钥，只在网页端设、看不到原文 |
| `main` | 生产分支：大家实际在用的那个版本 |
| `preview/dice-bot` | 预览分支（**长期保留**）：改动直接放这里验，验过才进 `main`；不用新建分支 |
| Worker Previews | Cloudflare 给的独立预览地址，数据与生产隔离 |
| 合并 / Merge | 把 preview 上验过的改动一次性搬进 `main` |
| Commit | 在 GitHub 上保存一次改动 |
| SPA 兜底 | 找不到的路径一律返回首页；所以别用 404 判文件在不在 |
