# 添加新规则的标准指引

> 日期：2026-10-29　适用：M3 架构（引擎已拆成 23 个 ESM 模块）
> **结论先说**：加一个新规则 = **新建 1 个规则包文件 + 改 6 处登记**。
> 主流程（`cmd.js`）**一行都不用改** —— 这不是推测，是实测过的（见第 5 节）。
>
> 改完必须跑 `node tools/check-rule-registry.js`，**全绿才算登记完整**。
> 漏登记任何一处都不会报错，只会静默半残。

---

## 1. 为什么"加一个包就行"只对了一半

主流程确实不认识任何具体规则（这条由 §22 的源码级断言守着）。但引擎里有 **6 处登记表**，
漏掉任何一处**不报错**，只会半残：

| 漏了哪处 | 会怎样（**不报错，只是悄悄不对**） |
|---|---|
| `RULE_META` | 顶栏 / `.status` 里规则名显示 undefined |
| `IMPLEMENTED` | 切规则时提示"尚未实现" |
| `rule` 别名 | `.set rule 新规则` 认不出来 |
| `CHECK_DOMAIN` | 新规则的技能名被别的规则抢走（同名词互相干扰） |
| `CARD_DOMAIN` | 角色卡字段认不出来 |
| `RULE_PACKS` | 直接取不到包 |
| `FAMILY_PACKS` | 角色卡按"它自己的族"渲染时取不到包 |
| `index.js` 导出 | 浏览器 / Worker 里根本没这个模块 |
| `help.js` | `.help 新规则` 没有子页 |

而 676 项断言**只测现有规则**，抓不到这些 —— 所以必须靠 `check-rule-registry.js` 扫。

## 2. 逐步清单（照着改）

假设新规则叫 `xyz`（引擎内部的键名，小写英文）。

### 第 1 步：新建 `packages/engine/src/pack_xyz.js`

必须实现的接口（**必选 7 个**，与 `check-rule-registry.js` 的清单一致）：

| 方法 | 作用 |
|---|---|
| `family` | 族名，如 `'xyz'` |
| `checkHint()` | 打错时提示正确用法 |
| `listChecks()` | `.rc list` 显示什么 |
| `checkOffNote()` | 跨规则误用时的提示 |
| `cardTemplate()` | `.st new` 的卡模板（不需要就返回 null） |
| `parseCard()` | 解析 `.st set` 的字段 |
| `renderCard()` | 渲染角色卡 |

> 卡的 HTML 渲染**不在包里**：`renderCardHtml()` 在 `card.js`（M3 解环时移出去的），
> 所有规则共用一份 —— 包只负责"卡上有哪些字段、怎么取值"。

**条件必选 2 个**：

| 方法 | 何时需要 |
|---|---|
| `runCheck()` | 仅当 `supportsCheck: true`（即支持 `.rc` 检定）时才需要 |
| `replayVerdict()` | 需要"从历史 payload 还原判定"时才需要（COC/DH/FU/D&D 都有） |

> ⚠️ `supportsCheck: false` 的包**不要**写空的 `runCheck` ——
> 空实现比没有更糟：看着支持，其实什么都不做。

最简单的起步：复制一个结构最接近的现有包（比如要 d20 vs DC 就抄 `pack_dnd.js`，
要双骰求和就抄 `pack_fu.js`），再逐个改。

### 第 2 步：`packs.js` —— 3 行

```js
import { XYZ_PACK } from './pack_xyz.js';                      // ①

const RULE_PACKS   = {..., xyz:XYZ_PACK};                      // ②
const FAMILY_PACKS = {..., xyz:XYZ_PACK};                      // ③
```

### 第 3 步：`rules.js` —— 3 处

```js
const RULE_META = {..., xyz:{name:'新规则', short:'新规则'}};  // ① 显示名
const IMPLEMENTED = new Set([..., 'xyz']);                     // ② 标记为已实现
registerAliases('rule', [                                      // ③ 别名（含中文）
  ...,
  {key:'xyz', display:'新规则', aliases:['xyz','新规则','别名1']}
]);
```

### 第 4 步：`domains.js` —— 2 项

```js
const CHECK_DOMAIN = {..., xyz:'check:xyz'};
const CARD_DOMAIN  = {..., xyz:'cardkey:xyz'};
```

> ★ 这两个表在 `domains.js`（**不在 `dnd.js`**）。
> M3 里专门把它们从 dnd.js 迁了出来：加新规则不该去改 D&D 的文件。
> 域名必须**互不相同** —— 退回单一域会让"潜行"这类同名词在不同规则下互相抢键。

### 第 5 步：`index.js` —— 1 行

```js
export * from './pack_xyz.js';
```

放在**其它 `pack_*.js` 之后**、`packs.js` 之前（export 顺序 = 别名注册顺序，
先到先得，顺序错了会有别名被静默抢走 —— 由 `check-engine-split.js` 第 ⑤ 项守着）。

### 第 6 步：`help.js` —— 加帮助子页

`.help xyz` 要能看。

## 3. 改完必跑的三条命令

```bash
node tools/check-rule-registry.js    # 登记完整性：漏一处就红
npm test                             # 796 项断言 + 端到端冒烟
npm run mutate                       # 确认你的新代码被引断言覆盖（不是摆设）
```

**第 3 条最容易被跳过，也最重要**：如果你的新规则逻辑没有任何断言能抓到它被改坏，
那它就是"没被验过"。加完规则至少补几条断言到 `tests/test_engine.js`。

## 4. 常见坑

| 坑 | 说明 |
|---|---|
| 只改了 `RULE_PACKS` 忘了 `FAMILY_PACKS` | 角色卡渲染时取不到包（卡有自己的族，不一定等于当前房间规则） |
| 别名没加中文 | 用户打中文规则名切不过去 |
| `replayVerdict` 只回 verdict | COC 的"为什么是这个等级"会丢 —— 历史消息与当时看到的差一行 |
| 在 `dnd.js` 里找域名表 | 已经迁到 `domains.js` 了 |
| 顺手改了 `cmd.js` | **不需要**。主流程不认识具体规则，改了反而说明抽象漏了 |

---

## 5. 这条结论是怎么来的（实测，不是推断）

我在引擎的一份**临时副本**里真的加了第七个规则包「探针」，跑通后删除了副本：

- ✅ `cmd.js` 的 diff **为零** —— 主流程一行没动
- ✅ 新规则的别名、包、族、域全部生效
- ✅ 原六规则全部不受影响

同时新增了 `tools/check-rule-registry.js`（15 项），并做了 **6 组变异验证**
（故意漏登记 / 故意让域名退回单一域），**全部变红** —— 说明这些检查不是摆设。

顺带一提：这次重构还修掉了一个拼接器的隐患 —— `load-engine.js` 剥 import 的正则
原本要求"分号后必须到行尾"，所以 `import {X} from './y.js'; // 注释` 会被漏过去，
导致拼接路崩在 "Cannot use import statement outside a module"。已放宽为允许行尾注释。
