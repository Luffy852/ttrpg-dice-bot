**必须注意的坑**（从手册第六节裁剪 + 本项目新增，★ = 本项目新增）：

*通用原则（手册原则 1–6 全适用）*
- **原则 6 派生值不存副本**：`total` / `highRoll` / 成功等级 / Hope-Fear 归属**全部现场推导**，不存进消息 payload。这与手册"列表 18、详情 13"是同一个病
- **原则 4 同一份渲染不写两遍**：骰子结果会出现在**三个地方**——聊天流气泡、详情面板（点开历史）、导出的战报。**必须共用同一个渲染函数**，差异只在渲染目标
- **原则 5 正交维度别绑死**：优劣势是「模式 × 作用于谁」两个维度（手册原坑）；本项目新增一组正交：**规则 × 角色卡**（规则切了但卡还是旧规则的 → 必须处理，不能静默）

*手册 6.2 前端通用（适用部分）*
- 严格模式下 `this` 丢失 → 引擎搬成 ESM 时，对象方法内的回调一律用箭头函数
- 监听器泄漏 → WebSocket 重连若每次 addEventListener 不 remove 会成倍泄漏；改单例 + 委托
- 固定区必须有 `max-height` + 内部滚动 → 聊天流上方的结果卡/房间信息栏
- grid 表头与数据行错位 → 列宽抽 CSS 变量共用（动作列表/角色卡表格会用到）
- 枚举型 UI 文案逐组合写 → **帮助文本与模式提示文案**高危（"其余正常投掷"指向空集那种）
- 窄屏重排用 `display:contents` → 双列布局在手机上整块堆叠时列内顺序无法重排
- CDN 单源 → 若前端仍用 CDN 库，主源 + 备用源自动回退

*★ 本项目新增：房间号与 PIN（6 位数字带来的新问题）*
- **★ 6 位数字必然可枚举** → 10^6 空间，任何知道号码的人都能尝试进入。**开放房间靠"号码不公开"这一层，不是靠不可枚举**。必须接受这个风险
- **★ 4 位 PIN 只有 10^4 组合** → 是**防误入**不是防攻击。必须配**同房间 PIN 校验失败限流**（复用 IP 令牌桶），否则可被暴力枚举
- **★ 撞号检测要"惰性创建式"** → 生成号码时访问该 DO 读 `meta.created_at`：不存在或已过期即占用成功；存在且未过期则重试（上限 5 次）。**不要**用 KV 维护已用号码集合（10^6 个 key，成本高且 KV 最终一致）
- **★ 号码空间要监控** → 稳态占用 = 30 天 × 日均新建数。撞号概率 ≈ 已占用数 / 10^6。**超过 10% 占用（10 万）需告警**；到 50% 时撞号率 50%，基本不可用
- **★ 别名新增前必须查冲突** → `inti`（威吓）不能简写成 `int`（智力）；`dnd5e2024` 与 `dnd5e` 互为前缀，故**必须精确匹配，不能前缀匹配**
- **★ PIN 只存 HMAC 摘要** → 静态资源与 DO 状态都可能暴露，不存明文
- **★ PIN 校验后发短期 token** → 存 `sessionStorage`（标签页级）：刷新不重输、关页即失效、换设备仍需 PIN
- **★ PIN 固化后，创建那一次展示是唯一一次** → 必须做三件事：① 创建成功页**显著展示** PIN ② 明确提示"此 PIN 不可修改、不可找回，请截图保存" ③ **房间号与 PIN 分开显示**（截图时极易只截到一个）
- **★ 固化带来的新风险：误设 PIN 无法撤销** → 手滑给开放房间设了 PIN 又没记全，整个群组永久锁死，且比"被改 PIN"更常见。对策：创建页"需要 PIN"**默认不勾选**；勾选后需**输入 4 位 + 再次确认输入**

*★ 本项目新增：后端与实时（手册零覆盖，见《手册增补草案_后端与实时》）*
- **客户端时间不可信** → 时间戳一律服务端生成
- **ws 重连必须幂等** → `msg_id` 去重 + 游标补齐，否则重连后消息重复或丢失
- **服务端掷骰要防重算** → 同一条指令只掷一次，重试不能重掷
- **并发 `.set rule` 竞态** → 后到为准 + 系统消息留痕（无房主，全员可改）
- **`DELETE` 不缩磁盘** → SQLite 删行后文件不收缩；日常只 DELETE，500M 触发才 VACUUM
- **DO 之间无全局视图** → "整个工具占多少"没人知道，500M 清理需额外 KV 索引 + Cron
- **静态资源完全公开** → HMAC secret 不能进前端；房间口令只存摘要

*★ v4 新增：真机验收轮才暴露的（详见 §4a-M4）*
- **★ ws 半开连接** → 手机息屏是系统直接掐网，**服务端收不到关闭帧**，那条连接在自己看来一直是 OPEN。
  `readyState` 过滤治不了 —— 必须记"最后一次收到帧"时间，超时主动关（本项目 3 分钟）
- **★ schema 迁移的老房间路径 ≠ 新建路径** → `CREATE TABLE IF NOT EXISTS` 对已存在的表什么都不做，
  新列要靠 `ALTER TABLE` 补。**索引必须建在 ALTER 之后**，否则老房间建索引抛 `no such column` → DO 构造崩
- **★ DO 构造函数崩 = 整个房间打不开** → 表现为 HTTP 500 + ws 关闭码 1006。
  构造期/握手期的**附属操作**（排闹钟、更新 last_seen）一律要包 try —— 它们只是记账，
  抛了就是房间彻底不可用，代价远大于"这条记账丢了"
- **★ 重排 seq 会让所有人的游标失效** → 必须广播让整房重载；且客户端要**先清空去重集合再重新拉**，
  否则服务端重发的一整屏会被判成重播而全部丢弃（表现是"导入完什么都没变"，比报错还难查）
- **★ 清理条件不能只看 ts** → 有了续期就必须改成「满 30 天 **且** 没被续期」；
  且续期要覆盖"已被导入救活的"（ts 过期但 `keep_until` 有效），否则接力链会"导一次断一跳"
- **★ `assets-upload-session` 失败（code 10013）是 Cloudflare 侧故障** → 直接 Retry build，
  **千万别改 Worker 名字绕过**（DO 命名空间跟着脚本名走 → 改名字 = 所有房间数据消失）

## 1. 目标与验收标准

**一句话目标**：
让跑团小队能开一个网页房间，用文字指令掷骰，全房间看到同一份不可篡改的骰点明细与规则判定结论。

**必须做到**：
1. 多房间：一个不可枚举房间码 = 一个房间，进同一房间的人实时看到彼此的消息与骰点
2. 服务端权威掷骰：客户端只发指令文本，结果在服务端生成后广播
3. 四套规则包：通用 / DND5E / DND5R / COC7 / DH / FU（含别名不区分大小写）
4. 角色卡：四套规则都能 `.st set` 绑定，未绑卡有友好提示不报错
5. 元指令：`.help`（分层）、`.status`、`.set rule`、`.set baredice`、`.name`
6. 30 天留存 + 导出（NDJSON 全量 + Markdown 战报）

**明确不做**（边界，比「要做」更重要）：
- 不做**暗骰 / GM / 权限分级**（原因：全员同权限，明骰即可，用户已决策取消）
- 不做**属性生成器联动**（原因：v1 统一走 `.st set`；未来做独立小工具生成指令串）
- 不做**资源追踪**（物语点 / 希望点 / HP / 压力）（原因：玩家自己记）
- 不做**骰池语法** `4d6k3` / `kh` / `dl` / `ro`、重复掷 `2#1d20`、括号优先级、乘除、万能骰 `dF`（原因：四套规则都不依赖）
- 不做**跨房间角色卡**（原因：角色卡严格房间内作用域）
- 不做自定义宏 / 表达式语言、不做可验证随机的实现（只留接口位）

**验收标准**（可量化，能一句话判定过没过）：

*引擎层（沙盒可验，纯逻辑单测）*
- 固定随机种子下，`rollPass('2d6+3')` 的 rolls 与 total 与期望值**逐字段相等**
- 四套规则包各跑一遍**判定样例表**（输入点数 → 期望结论），全绿
  - COC：技能 60 掷 23 → 困难成功；掷 01 → 大成功；掷 100 → 大失败
  - DH：双 d12 同点 → 关键成功（即使低于难度）
  - FU：双 1 → 失手；双 8 → 暴击；HR = 两骰较高者
  - DND5R：掷 20 → 成功（任意检定）；DND5E：仅攻击/死亡豁免必中
- 优劣势：DND 下 `.r 1d20+2d6+3 adv` → **只有 d20 投两次**，2d6 投一次

*协议层*
- 同一 `msg_id` 重复投递两次 → 客户端只渲染一条（幂等）
- 断线重连后用游标补齐 → 无重复、无遗漏

*呈现层（需用户拍板）*
- 见第 5 节 M1 —— **B 段第一轮必须先出 A/B/C 三版模拟渲染**（手册 §5-⑤ / 框架第二章类型 5）

*性能*
- 单房间 8 人、500 条消息的首屏加载 < 2 s
- 单条指令从发送到全员可见 < 500 ms（含往返）

| 随机源 | `crypto.getRandomValues` | 可审计，不用 `Math.random` |
| 权限模型 | **全员同权限，无 GM、无房主** | Q13 已答取消暗骰与分级 |

| **★ 容量护栏**（v4 定） | **软提醒**（超 5000 条提示），不硬拦 | 主动维护的体量有限；硬拦会在真有历史要接力时卡住 |
| **★ 时区**（v4 定） | 全项目 **UTC+8**，走 `util.js` 的 `hhmm/ymd/ymdhm` | 服务端跑 UTC、前端按浏览器时区 → 同一条消息两个时间，差 8 小时 |

| 暗骰 / GM / visibility 列 | 用户明确取消（Q13），且是 v0.1 的最高风险项 |
| 通用表达式引擎 / 自定义宏语言 | 无底洞，四套规则都不需要 |
| 自动推断角色卡 | 只认显式 `.st set`，不猜 |
| 属性生成器一键填卡（v1） | 用户反馈 3：v1 统一走指令 |
| 服务端 VACUUM 每次清理都跑 | 锁库且耗时；仅 500M 触发时才跑 |
| **不可枚举长随机码作为主防护** | 用户明确要 6 位数字（Q26 已定）。改为：6 位数字 + **可选 4 位 PIN**，PIN 是主防护 |
| **PIN 可修改（需原 PIN）** | 用户改定：**PIN 创建即固化**。可改会让个别成员把整个群组锁在外面，风险大于收益 |
| **开放式房间后加 PIN / 有 PIN 房间取消 PIN** | 同上风险性质（任何成员都能挡住其他人），对称性禁止 |
| **KV 维护已用号码集合** | 10^6 个 key 成本高且 KV 最终一致；改为惰性创建式撞号检测 |
| **熟练加值自动计入检定** | 需维护"哪些技能熟练"这份额外数据，属资源追踪同类；改为 `.rc <技能> p` 显式声明（✅ 已定） |
| **导出筛选的 UI** | v1 不做；但接口与 `idx_sender` 现在就备好 |

| **导入消息绝对豁免清理**（v4 否决） | 无上限堆积。改为"每次导出/导入续 30 天" —— 保留默认清理，只在用户明确要时延长 |
| **重排时把 seq 压回 1..N**（v4 否决 · G 组） | 会生成已被占用的 `msg_id`（清理删过老消息时尤其容易）→ UNIQUE 报错 → 指令丢失。改为从 `room.seq+1` 起分配 |
| **续期写进 ts**（v4 否决 · H 组） | ts 是发生时间 + 排序键 + 内容的一部分。改了会让老消息假装是刚发生的（重排错乱、战报时间全错） |
| **硬上限拒绝导入**（v4 否决 · H 组） | 会在真有历史要接力时卡住；改为软提醒 |
| **导入时给陌生人建成员记录**（v4 否决） | 虚增"累计接入人次"，且他们没有角色卡与在线状态 |
| **改 Worker 名字绕过 assets 上传失败**（v4 否决 · ★危险） | 房间数据在 Durable Object 里，DO 命名空间跟着 Worker 脚本名走 —— **改一次名字 = 全部房间数据消失**。遇到 `assets-upload-session` 报错（code 10013）应直接 Retry build |

**★ 方法论提炼（5 条，比具体 bug 重要）**

1. **测试替身不能抄生产逻辑**（#18）。抄一份迟早各错各的 —— 而且错的那份在测试里永远绿。
   凡是"为了测试方便复制一段生产逻辑"，都要改成**抽出来共用同一份**。
2. **单测的盲区在"胶水层"**（#19）。网关转发、序列化、字段映射这类代码，
   单测往往绕开它们直接调核心。**端到端真跑是唯一解** —— 这也是为什么沙盒里要起 workerd。
3. **生成物与手工修改互斥**（#20）。凡"由脚本生成的文件"，一律改脚本，
   并在脚本里加断言锁住结果，否则改动会在下次生成时静默消失。
4. **"新房间正常"不等于"老房间正常"**（#17 #21）。schema 迁移类改动，
   老数据的迁移路径和新建路径**不是同一条代码路径**，必须各测一遍。
5. **断言自己也要被验证**（#22）。先红后绿不是走过场 —— 
   如果绿了却说不出"它到底在防什么"，那条断言多半是摆设。

**暂存 3**（B 段 M1 真机，4 条反馈，已修）
- 症状（用户真机 Chrome + 手机浏览器，一轮就提了 4 条）：① 自己发的指令不在消息记录里，打错了看不见、没法回溯 ② 帮助文本用等宽 `<pre>` 输出，窄屏换行后**指令与说明粘成一坨**分不开 ③ 骰点高亮过宽 —— **d6 掷出 1 也被标黄**，而 1 对 d6 毫无语义 ④ 顶栏快捷指令 11 个太多，横向滚动**显示不全**
- 真实病因：
  - ①**把"输入"当成了 UI 控件状态而非数据**。聊天工具里"我说了什么"本身就是消息，进不进记录是产品决策不是实现细节
  - ②**说明性内容用纯文本传输**（手册 6.2"枚举型文案"的近亲）：纯文本没有结构，窄屏只剩"换行"一种排版手段 → 必然混淆。必须**结构化传输（k/v），由渲染层决定分栏还是堆叠**

## 0. 通用约定

### 0.1 指令前缀
以 `.` `/` 开头触发指令。**中文句号 `。` 与全角句点 `．` 同样有效**。未命中动词 → 当作普通聊天发出，不报错。

### 0.2 中文别名（★ 全局生效 + M2 分域）
所有"用户输入的名字"都走同一个别名层：动词 / 规则名 / 属性 / 技能 / 特性 / 卡字段 / 优劣势 / 开关 / 熟练，全部中英文都认。

归一化：`NFKC`（全角转半角）→ 小写 → 去空格与下划线，**保留点号**（`5.5e` ≠ `5e`）。

**★ M2 起按规则族分域**（`check:dnd` / `check:coc7` / `check:dh` / `check:fu`，卡字段同理）：
D&D 的「潜行」是 stealth、COC 的「潜行」是另一套东西；「力量」在四族里各是各的。
共用一个域会互相抢键（先到先得，后注册的静默失效）—— **分域 = 让入口不重叠，同时仍只有一个入口**。

### 0.3 别名冲突
注册时先到先得，冲突进 `ALIAS.conflicts`，**不静默覆盖**。新增前用 `detectConflicts()` 自查。
已知易混：`int` = 智力 vs `inti` = 威吓；`感知`（WIS 属性）vs `察觉`（Perception 技能）；COC 的「急救」与「医学」都曾写 `medicine`（M2 已修）。

| 规则 | 绑卡写法 | 字段 |
|---|---|---|
| **D&D** | `.st set 力量 16 敏捷 14 体质 15 智力 10 感知 12 魅力 8 等级 5` | 六属性（1–30）+ 等级（1–20） |

| **最终物语** | `.st set dex d8 ins d10 mig d8 wlp d6` | 四属性骰阶（d6/d8/d10/d12，写 8 同 d8） |
| **通用** | 不使用角色卡 | `.st` 给"本规则不用卡"的说明 |

## 5. COC 7th 规则包

### 5.0 属性（★ 2026-11-01 补：原来只有技能、没有属性，连体型 SIZ 都没注册）

**八大属性 + 幸运，全部按百分比存（1–99）**，与技能同值域、同检定链（都是 1d100 ≤ 数值），
差别只在**卡面分类**与**派生值**：

| 中文 | 英文 | 中文 | 英文 |
|---|---|---|---|
| 力量 | str | 智力 | int |
| 体质 | con | 意志 | pow |
| **体型** | **siz** | 教育 | edu |
| 敏捷 | dex | 幸运 | luck |
| 外貌 | app | | |

**派生值（由属性现场推导，不进卡 —— 原则 6）**：
HP =（体质+体型）/10 向下取整　·　MP = 意志/5 向下取整　·　SAN 初始 = 意志　·
DB / 体格 =（力量+体型）查表（≤64 −2　65–84 −1　85–124 0　125–164 +1d4　165–204 +1d6）
**缺哪个属性就少哪一项**，不拿半个属性凑一个假数。`MOV` 移动速度不做（内部口径，不向玩家披露）。

**★ 派生值怎么进卡（2026-11-02 真机反馈定稿）**：设定属性后，卡面**条件显示**一句
「属性派生值分别为 HP … / MP … / SAN … / DB … / 体格 … —— 复制下面这行一次性录入：」，
外加一条算好结果的 `.st set HP 11 MP 14 SAN 70 DB 0 体格 0`。玩家复制粘贴发一次即可录入；
**派生备忘字段（hp / mp / san / db / 体格）任何一个已录入 → 整块提示消失**，卡面只剩玩家自己填的
备忘行。不再常驻「派生」行 —— 否则与备忘行两行并列、内容几乎一样，观感很差。

**★ 7 版没有「灵感」这一属性**：灵感检定 = 智力检定（掷骰 ≤ 智力值）。卡上若写了「灵感」，那是用户自定义的技能名。
**★ 「体型」（SIZ 属性）与「体格」（Build 备忘）是两个词、两个字段**：体格是**可手填**的备忘字段。
**DB（伤害加值）也是可手填备忘字段**，走宽松值域（−2 / 0 / +1d4），**不是 1–99 的百分比技能** ——
原先没注册，写 `.st set DB 0` 会被「需在 1–99」拦下（已修）。

### 5.1 检定 `.rc`
```
.rc 侦查              掷 1d100 vs 数值，输出成功等级（属性同样能掷）
.rc 力量              属性检定，与技能同一条链
.rc 侦查 +1           1 个奖励骰（十位取低）
.rc 侦查 -2           2 个惩罚骰（十位取高）
.rc 侦查 +1 -1        1 奖 1 罚 → 相抵
.rc 侦查 奖励1        中文同样认（奖 / 罚 / 奖励 / 惩罚）
.rc list              列出卡上的**属性与技能**（分两栏）
```

**成功等级**（技能值 60 时）：掷 23 → 困难成功（≤30）；掷 01（或技能 ≥50 时的 01–05）→ 大成功；
掷 100（或技能 <50 时的 96–100）→ 大失败；≤1/5 → 极难成功；≤1/2 → 困难成功；≤技能值 → 成功。

**奖惩骰 `rollPercent()`**（COC 包里唯一的新掷骰逻辑）：十位骰若干 + **共用个位骰**；奖励取十位最低、惩罚取十位最高；奖惩相抵后按净额投额外十位骰（上限 8 颗）。十位 00 + 个位 0 = **100**。

**未绑卡**：给 COC 专用提示（先 `.st set 力量 60 体质 50 体型 60 …` 填属性，再 `.st set 侦查 60` 补技能，或 `.r 1d100` 裸掷），不用 D&D 那句。
**技能不在卡上**：提示"卡上还没有「X」的数值 —— 用 `.st set X 60` 添加"。

## 6. 匕首心规则包

### 6.1 角色卡
六特性：敏捷 Agility(agi) / 力量 Strength(str) / 灵巧 Finesse(fin) / 本能 Instinct(ins) / 仪态 Presence(pre) / 知识 Knowledge(kno)，调整值 −1 ~ +3。

### 6.2 动作掷骰 `.dh`（★ 规则专属动词）
```
.dh 15          希望骰 d12 + 恐惧骰 d12 vs 难度 15
.dh 15 敏捷     取卡上「敏捷」的调整值计入总和
.dh 15 +2       直接给调整值（可写 -1）
.dh 15 优势     额外 +1d6 计入总和
.dh 15 劣势     额外 −1d6 计入总和
.dh             只掷不判难度
.dh 难度15      中文难度写法
```
**判定四象限**：合计 ≥ 难度 ×（希望 > 恐惧 ? 成功带希望 : 成功带恐惧）；< 难度 × 同理。
**关键成功**：双骰同点 → **即使低于难度也必定成功**，获 1 希望、可清 1 压力。
**★ Hope/Fear 只看两颗 d12** —— 优劣势加减的 d6 不参与比较。
**未绑卡**：可以掷，但明确说明"「敏捷」调整值按 0 计算"（不静默）。
**本规则不用 `.rc`**：`.rc` 会提示改用 `.dh`；`.rc list` 给六特性清单。

## 7. 最终物语规则包

### 7.1 角色卡
四属性骰阶：DEX 敏捷 / INS 洞察 / MIG 力量 / WLP 意志，各 d6 / d8 / d10 / d12。

### 7.2 检定 `.fu`（★ 规则专属动词）
```
.fu dex ins 10     用卡上的 DEX + INS，对 DL 10 检定
.fu dex dex 13     同一属性可用两次
.fu d8 d10 10      无卡时直接给骰阶（必须带 d）
.fu dex ins        只掷不判难度
.fu dex ins 难度13 中文难度写法
```
**难度参考**：7 易 / 10 普通 / 13 困难 / 16 极难
**★ 高骰 HR**：两骰较高者（攻击伤害用），每次结果都给出。
**★ 暴击**：双骰同点且 ≥6 → 无视难度必定成功 + 1 次机会。
**★ 失手**：双 1 → 必定失败且事态恶化，获 1 物语点。
**没有优劣势**：带 adv/dis 会提示"重掷请再发一次同一条指令"（v1 不追踪物语点）。
**本规则不用 `.rc`**：`.rc` 会提示改用 `.fu`；`.rc list` 给四属性 + 难度参考。

## 8. 规则包接口（★ M2 扩展后的契约）

```js
{
  family,                     // 角色卡族
  supportsCheck,              // 支持 .rc 吗（DH/FU = false）
  needsCard,                  // 检定必须先绑卡吗（COC/D&D = true，DH/FU = false）
  checkHint(),                // .rc 无参数时的一行用法
  listChecks(ruleKey, card),  // .rc list 的内容（defs 结构）
  checkOffNote(ruleKey),      // 不支持 .rc 时的提示
  noCardNote(),               // 需要卡但没卡时的提示（COC 有专用文案）
  cardTemplate(),             // 无卡时 .st 给的模板（null = 本规则没有卡）★M2
  parseCard(rest),            // .st set 解析 → {data, errs, count}          ★M2
  renderCard(card),           // 卡渲染（栅格 HTML）                        ★M2
  cardExtra(card),            // 卡下方的附加行（D&D 的熟练加值）           ★M2
  runCheck({args, mode, card, ruleKey, me}), // 检定逻辑（返回 {view} 或 {notice}）★M2
  verbs: { dh: fn, fu: fn }   // 规则专属动词                               ★M2
}
```

**加新规则 = 加一个对象，主流程一行不动。** 凡是"内容随规则变"的查询一律挂规则包，不许在主流程里 `if-else` 分规则。

**★ 动词归属 `verbOwner(verb)`**：`.dh` 属匕首心、`.fu` 属最终物语。在别的规则下打了它 → 提示"这是 X 的专属指令，用 `.set rule x` 切换"，**不静默降级为聊天**。

## 9. 消息与呈现

### 9.1 消息模型
`{ id, ts, kind, from, actor, ... }` —— `from` = 谁说的；`actor` = 动作发起人（M3 多人时靠它知道这颗骰是谁掷的）。

5. **★ 骰点 chips 带语义标签**：COC「十位 / 个位」、DH「希望 / 恐惧」、FU「DEX / INS」——
   两颗骰并排时没有标签就分不清谁是谁（`[8][3]·[6]` 会被读成 83 和 6）

### 9.3 顶栏快捷指令（7 个，点击只填输入框）
