#### ★ 跨阶段前置约束（现行边界 · 结论；详解见附录 G）

> 以下九条口径、B1–B3、alarm 形态与五个实现坑**由用户拍板，是贯穿 S2 的现行设计前提（封板后仍为边界）**；附录 I 不得重定义。若设计稿出现「先攻表不受消息清理影响」「房间过期释放号码」「提醒落成系统消息」等表述，**一律以本节 / 附录 G 为准**。优化补完轮**只锁约束、不实现**重置 / 提醒改造 / alarm 重构 / `reset_at` 列。

**（1）房间生命周期九条口径**（详解见 G·8.1）

| # | 口径 |
|---|---|
| 1 | 房间**永不过期**；创建过的 6 位号码**永久占用、不回池** |
| 2 | 达到「30 天 或 消息续期时限，孰晚者」后，房间内**所有消息内容、辅助表格、访问记录一律清除** |
| 3 | 还原之后再访问，等同**一个类似全新房间**（号码、PIN、seq 墓碑保留） |
| 4 | 用户动作产生的 `notice` 留痕**计入计时**；任何用户主动动作都视作房间存活 |
| 5 | 只有**最后一条需清除信息被清除那一刻**才连带清空辅助状态、还原房间 |
| 6 | **重置不落任何消息**；提前 7 天提醒也不得落成系统消息（否则计时主体自续、永不到期） |
| 7 | `seq` 与 PIN 属**墓碑**：不得重置 `seq`、不得删 `room` 行、不得清 `pin_hmac` / `pin_salt` |
| 8 | 计时主体**只读 `messages`**；`last_active` / 辅助表行数都不得当判据（alarm 自己续写会自锁） |
| 9 | 清空事件**不是排程点**：某次 alarm 滚动 DELETE 后「由非空变空」，在**同一次 alarm 里**清辅助表、应用 B1–B3、`notified_clean=0`、不排新闹钟 |

| | 口径 |
|---|---|
| **B1** | **PIN 保留**：`pin_hmac` / `pin_salt` 属墓碑，任何清理路径不得清除。代价是「全新房间」仍带锁 |

**（3）alarm 形态与五个实现坑**（详解见 G·8.5）

- 形态：逐条滚动 DELETE 只动 `messages`；「由非空变空」那一次才归零；半开连接巡检与 30 天清理同一次 alarm。**〔D1 订正：本句是模块 B 的形态；2026-11-14 起巡检与生命周期已拆开，见下（5）〕**
- 五个坑：① 重置路径写新消息 → 计时主体自续；② `last_active` 被 alarm 自己续写 → 房间永不清；③ 提醒落成系统消息 → 同上；④ 辅助表行数混进「是否仍有可清除信息」判据 → 空房间永不重置；⑤ 把辅助表挂进逐条 DELETE 的级联 → 战斗打到一半条目消失。

**（4）设计口径与实现状态**：v10 登记的「只删 `messages` / `idempotency`」「提醒落系统消息」「还原路径没有」是 **S1 旧现状**；模块 B 第二包已全部改造（`lifecycle.js` 单一源、归零还原静默清 `combat_entry → combat → pcs → members`、提醒改不落库的 `STATE` 瞬时帧），`check-lifecycle.mjs` 守卫**转正为正向断言 ⑤–⑪**。九条口径 / B1–B3 / 五个坑**仍是现行设计前提，未变**。

**（5）★ D1 用量根治口径（用户 2026-11-14 拍板 · 新增，不重开上述九条 / B1–B3 / 五个实现坑）**：

| 项 | 口径 |
|---|---|
| 免费方案前提 | **不升级 Workers 付费方案**；Cloudflare DO SQLite 免费额度 **5,000,000 `rows_read` / 日、账户级（含 preview 实例）、00:00 UTC 重置**是硬约束，代码必须适配它 |
| 周期 | **过时消息清理按日一次已足够，根本不需要高频遍历**；`LIFECYCLE_MS = DAY`，`nextAlarmAt` 不再把「在线 ws」或「下一条到期」当短周期候选 |
| 巡检与生命周期解耦 | 半开连接巡检**改由 ws 帧驱动**（收到任意帧 → `sweepIdleThrottled()`，内存节流 `SWEEP_MS`、纯 ws 遍历、零全表 SQL）；`IDLE_MS=180s` 与 20s 心跳的清理语义**不变**。alarm 链不再调 `io.sweepIdle()`、不再每轮写 `last_active`、不再算 `SQL_MIN_EXPIRY` 表达式全表聚合 |

> 九条口径 / B1–B3 / 五个实现坑 / 归零与提醒语义**一条未变**；D1 只改「多久跑一次、由谁触发、用哪条 SQL 判存在」。详解与旧形态留痕见附录 G·8.5。

**A.2 nat 语义（★ 按规则分化）**：**D&D 5.5e(2024)**：自然 20 强制成功（✨ 金徽章）、自然 1 强制失败（💀 红徽章）；**D&D 5e**：不自动成功 / 不自动失败，照常计算（⚡ 标注）；**通用 / COC / DH / FU**：**无高亮、无徽章、无说明**。高亮只对单颗 d20 生效（`critOf(sides,v,ruleKey)`），d6 掷 1 是普通结果 —— **没有语义的东西就不要提**。

**A.3 元指令**：`.help`（`.帮助` / `.说明` / `.用法` / `.菜单`，带规则专属页）、`.status`、`.set rule <键>`、`.set baredice on`、`.name`、`.h`、`.st`（★ 四套规则统一角色卡入口）。**A.3.1 规则名中英文都认**，六个规范键：`generic` / `dnd5e` / `dnd5r`（5.5e·2024）/ `coc7` / `dh`（匕首心）/ `fu`（最终物语）；逐条别名表见 v13 附录 A.3.1。**A.3.2 开关值** `on/true/1/开/开启/是/启用/yes` ↔ `off/false/0/关/关闭/否/停用/no`；**A.3.3 裸骰**默认关，开启后整条是纯骰表达式才掷。

**A.4 角色卡 `.st`（★ 四套规则统一入口）**：`.st` 是**元指令** —— 模板 / 解析 / 渲染全部由**当前规则的包**提供，已绑定的卡按**卡自己的族**渲染（正交维度）。D&D 六属性（1–30）＋ 等级（1–20）；COC **开放技能表**（1–99）＋ hp/san 静态备忘；匕首心六特性调整值（−1~+3）；最终物语四属性骰阶（d6/d8/d10/d12，写 `8` 同 `d8`）；**通用不用卡**。`.st` 查看 / `.st clear` 解绑 / `.st set` 同族合并换族换卡（**换族覆盖必须明说「原 X 卡已被替换」，不静默**）；**卡属于卡自己的规则**（通用规则下看 D&D 卡仍按 D&D 渲染并提示切回）。**COC hp/san 是静态备忘，骰娘不自动增减**（这正是 `.sc` 只掷不改卡的依据，I·4.1）。D&D 熟练加值由等级派生、只显示不自动计入。

**A.5 COC 7th 规则包**：**A.5.0** 八大属性 ＋ 幸运按百分比存（1–99），与技能同检定链（1d100 ≤ 数值）；**派生值现场推导、不进卡**（原则 6）：`HP=(体质+体型)/10↓`、`MP=意志/5↓`、`SAN 初始=意志`、`DB/体格=(力量+体型) 查表`，**缺哪个属性就少哪一项**；`MOV` 不做。设定属性后卡面**条件显示**派生值提示 ＋ 一行算好的 `.st set HP…`，**任一备忘字段已录入 → 整块提示消失**。**7 版没有「灵感」属性**（＝智力检定）；**「体型」SIZ 属性与「体格」Build 备忘是两个字段**，`DB` 是可手填备忘（非 1–99 百分比）。**A.5.1 `.rc`**：1d100 vs 数值输出五级成功等级；奖惩骰 `rollPercent()`（十位骰若干 ＋ **共用个位骰**，奖励取十位最低、惩罚取最高，净额上限 8 颗；十位 00 ＋ 个位 0 ＝ 100）是 COC 包唯一的新掷骰逻辑。**A.5.2 技能别名是开放表**（不在表里的名字照收进卡、照样能 `.rc`）；**属性不在技能表里**。逐条对照见 v13 附录 A.5.2。

**A.6 匕首心规则包**：**A.6.1** 六特性（agi / str / fin / ins / pre / kno，−1~+3）。**A.6.2 `.dh`**（规则专属动词）：希望 d12 ＋ 恐惧 d12 vs 难度，可带卡上调整值 / 直接给值 / 优劣势额外 ±1d6；**判定四象限**（≥ 难度 × 希望>恐惧 ? 成功带希望 : 成功带恐惧）；**双骰同点 ＝ 关键成功，即使低于难度也必定成功**；**Hope/Fear 只看两颗 d12**（优劣势的 d6 不参与）；未绑卡明说「调整值按 0 计算」；不用 `.rc`。

**A.7 最终物语规则包**：**A.7.1** 四属性骰阶 DEX / INS / MIG / WLP（d6/d8/d10/d12）。**A.7.2 `.fu`**（规则专属动词）：两属性或直接给骰阶（必须带 `d`）对 DL 检定（7 易 / 10 普通 / 13 困难 / 16 极难）；**高骰 HR** 每次都给；**双骰同点且 ≥6 ＝ 暴击**、**双 1 ＝ 失手**（必定失败且事态恶化）；**没有优劣势**；不用 `.rc`。

**A.8 规则包接口契约（★ 全文留 · 未来加规则 / 加动词的唯一约束）**：

## G·8. 跨阶段已定边界（自完备收录）

> 本章是**房间生命周期的现行边界**（由用户拍板、封板后仍生效）；优化补完轮「只锁约束、不实现」，模块 B 第二包已按此实现归零还原，D1 再改「多久跑一次 / 由谁触发 / 用哪条 SQL 判存在」。附录 I 应**以此为准，不重复定义、不与之冲突**。

### G·8.1 九条已定口径

| # | 口径 |
|---|---|
| 1 | 房间**永不过期**；创建过的 6 位号码**永久占用、不回池** |
| 2 | 达到「30 天 或 消息续期时限，孰晚者」后，房间内**所有消息内容、辅助表格、访问记录一律清除** |

### G·8.3 模型速记（压缩为结论）

> v13 曾用代码块逐层画「计时主体 / 锚点 / 清空事件 / 墓碑」；v14 保留结论，逐层原文见 `docs/archive/` 的 v13 附录 G·8.3。

- **计时主体** ＝ `messages` 全 kind（含用户动作 `notice` 留痕）＋ `idempotency`；单条到期 `keep_until IS NULL ? ts+30d : keep_until`；用户动作 / 导出续期不断后推最后到期时刻 → 「持续使用 ＝ 房间持续存活」自动成立。
- **锚点**（`room` 列，非执行指令）：`reset_at = max(每条到期时刻)` **只由用户动作刷新，alarm 绝不写**；`warned_for_reset_at` 防重复提醒；`notified_clean` 归 0 后可再触发。
- **清空事件不是排程点**：某次 alarm 滚动 DELETE 后「由非空变空」→ **同一次 alarm 里**清辅助表、应用 B1–B3、`notified_clean=0`、`reset_at` 置空、不排新闹钟。
- **墓碑永不清**：`room` 行（code / `created_at` / `pin_hmac` / `pin_salt`）＋ `room.seq`（压回 `1..N` 会撞已导出战报的 `msg_id` → UNIQUE 报错 → 指令丢失）。
- **分界线很干净**：进不进 `messages`、带不带 `ts` / `keep_until`。提醒与重置都不进，不会伪装成用户动作。

---### G·8.4 重置那一刻具体发生什么（压缩为结论）

> v13 的逐项平实清单与两张对照表已提炼；结论如下，逐条原文见 `docs/archive/` 的 v13 附录 G·8.4。

- **先分清两件事**：用户发 `.set rule` / `.set baredice` 是**主动指令**（落一条 `notice`、房间续活 30 天、顶栏变化）；重置时写回默认是**重置动作本身的一步**（B2，零气泡、零消息、零续活、只改字段 ＋ `STATE` 帧同步顶栏）。
- **提前 7 天提醒**：不产生消息、`seq` 不跳；`room` 里记「这次警告对应哪个预计清空时间」防重复；顶栏横幅 ＋ **不落库的瞬时帧**让在线的人立刻看到。用户不管 → 什么都不发生；点导出 → 给现有消息续 30 天、横幅消失、预计时间后推。
- **重置那一刻**（最后一次 DELETE 把可清除信息删空）：**删**所有消息 / 幂等记录 / `members` / `pcs` / `combat*` 等全部辅助表；**改写** `notified_clean=0`、`reset_at` 置空、累计人次归零、B2 写回默认、B1 **PIN 字段不动**；**绝对不动**房间号 / `created_at` / `seq` / PIN；**绝对不做**插消息 / `allocSeq()` / 写 `last_active` / 调 `deleteAll()`（＝释放号码，与口径 1 冲突）/ 排下一轮闹钟。**聊天流一条气泡都不新增**。
- **界面（不落库）**：在线的人收到瞬时帧 → 旧消息列表清空、顶栏规则刷回默认、人数归零、横幅消失；之后进来的人拿到空房间，`meta` / `.status` 里能看到「本房间已于 X 重置」——**读房间字段，不是聊天消息**。实际 HTTP 入口是 `GET /api/room/<code>/meta`（返回 `last_reset_at` / `server_now`），**常规前端进房不请求它**（§0.2）；`.status` 那一行由 P3 实现、真机侧待观察（§0.6）。
- **重置之后**：老链接刷新进来是空房间；谁发第一条消息就从那一刻重新开始 30 天计时（新一轮，不是上一轮续命）；一直没人发就一直空着、不排闹钟、不空转。
- **续活对照**：掷骰 / 聊天 / `.st` / `.set` / 导入 ／ 导出（不新增消息但续期）＝ **会续活**；提前 7 天提醒 / 房间重置本身 / 纯访问刷新 / 看到警告不动作 / 程序化扫房间 ＝ **不会**。

---### G·8.5 alarm 的新形态与五个实现坑

500 MB 全局 KV 监测取消的是「跨 DO 容量巡检」，**不是 alarm**。`alarm()` 一直是每个房间自己的定时器：滚动 `DELETE`（S1 实测 DELETE 后磁盘立即回落）、`sweepIdle()` 关半开 ws、提前提醒（改瞬时）、以及新增的「计时主体归零时清辅助表」。完全删掉它，沉睡房间只能等下次访问才惰性清理，与口径 5 不符。

**有意义的容器** = 有在线 ws **或** 计时主体里还有未到期内容 **或** `reset_at` 未过。三者皆无 → **不排新闹钟**，DO 休眠等请求唤醒。有内容时取 `min(下次 idle 巡检, 下一条到期时刻, reset_at−7d, reset_at)` 作为**唯一**闹钟时间（每个 DO 同时只能有一个 alarm，`setAlarm()` 覆盖已有的）；**排到 `reset_at` 只为保证那次 `DELETE` 一定发生，是否还原仍以 `DELETE` 后 `COUNT=0` 为准**，不在时间点上无条件清空。重新 arm 只放在明确的用户请求路径（`join` / ws 握手 / 发指令 / `/export` / `/import`），并用 `getAlarm()` 判断是否已排、只在需要提前时覆盖；**构造函数里不许无条件 `setAlarm()`**（DO 休眠唤醒时构造函数先于 `alarm()` 执行，会干扰已排闹钟）。

| # | 坑 |
|---|---|
| 1 | **重置不能落消息**：新消息 `ts=now` 重新起算 30 天 → 计时主体永不归零 |
| 2 | **提醒不能落消息**：现 `alarm()` 把提醒写成 `kind:'sys'` 的 `messages` 行，`insertMsgs()` 不带 `keep_until`（默认 NULL）自带 30 天寿命；`/export` 续期 SQL 不排除 `sys`，按提醒去导出时提醒自己被再续 30 天 → 自续环 |
| 3 | **`notified_clean` 判定要重做**：现为 `now − created_at > 23d` 且只置一次；改成按 `reset_at − 7d`、每轮可再触发，文案改为「本房间内容将重置」 |
| 4 | **不调用 `deleteAll()`**：DO 写过 storage 后不自行消失，必须显式 `deleteAll()` 才停止计费/消失；但调它等于**释放号码**，与口径 1 冲突。**「停 alarm」≠ 销毁容器** |
| 5 | **★ `last_active` 不能当存活锚点**（代码实测）：全仓只有两处写它 —— ws 握手（`room.js` 第 498 行）与 **alarm 第 649 行每次都写 `now`**；`join` / `meta` / `/export` / `/import` 全都不写。拿它当判据，自我续期的 alarm 会让空房间**永远不重置**。必须另立 `reset_at`，且 alarm 绝不写 |

### J·1 Cloudflare Worker Previews · 四层配置模型（★ 最有价值的沉淀）

| 层 | 内容 | 坑 |
|---|---|---|
| ① 账户级资源 | KV / DO namespace 等 | 删资源 ≠ 删引用 |
| ② 生产绑定 | `wrangler.toml` 顶层 `[[durable_objects.bindings]]` | **顶级配置一条不动** |
| ③ Previews Base / 模板 | `[previews]` 块，影响**新建** Preview | 空块 → 缺 `ROOM` → 建房 500（#36） |
| ④ **已存在的 Preview 对象快照** | 该对象保存着绑定快照，**改 Base 不影响它**（官方口径） | 残留 KV 绑定 → 10041（#35）；排查要连这一层一起清 |

- 预览命令字段（Settings → Build）默认 `npx wrangler preview`（open beta），**硬性要求配置存在 `previews` 块**（#34）。
- **「运行时绑定」不继承生产设置**：凡代码通过 `env.X` 读取的，都要在 `[previews]` 里再声明一次。`index.js` 的 `env.ROOM.idFromName(code)` 属于此类 → `[[previews.durable_objects.bindings]]` 必须写 `ROOM` / `RoomDO`。
- `PIN_SECRET` 生产与每个 Preview **各有独立槽位**（#37），新开预览实例要单独补一次；**绝不轮换**。
- `[previews]` **只影响预览构建**；`wrangler deploy`（生产 `main`）行为不变。Cloudflare 为每个 Preview 自动 provision 独立 DO namespace，**预览房间数据与生产完全隔离**。

### J·3 判据订正（★ 别再用错）

- **判通过看真实响应体，不靠日志数字**（`Read N files` 是枚举条目数，排除规则在其后才生效）。
- **只有 `.` 开头点文件走 `Add file → Create new file` 手打含前导点的完整名**，并在 commit 变更列表里核对；**普通新文件正常拖拽上传即可**，指引不要把「新文件」一律写成手动创建。
