#### ★ 跨阶段前置约束（S2 开工必读 · 结论；详解见附录 G）

> 以下九条口径、B1–B3、alarm 形态与五个实现坑**由用户拍板，是功能开发轮的设计前提**；附录 I 不得重定义。若设计稿出现「先攻表不受消息清理影响」「房间过期释放号码」「提醒落成系统消息」等表述，**一律以本节 / 附录 G 为准**。优化补完轮**只锁约束、不实现**重置 / 提醒改造 / alarm 重构 / `reset_at` 列。

**（1）房间生命周期九条口径**（详解见 G·8.1）

| # | 口径 |
|---|---|
| 1 | 房间**永不过期**；创建过的 6 位号码**永久占用、不回池** |
| 2 | 达到「30 天 或 消息续期时限，孰晚者」后，房间内**所有消息内容、辅助表格、访问记录一律清除** |
| 3 | 还原之后再访问，等同**一个类似全新房间**（号码、PIN、seq 墓碑保留） |
| 4 | 用户动作产生的 `notice` 留痕**计入计时**；任何用户主动动作都视作房间存活 |
| 5 | 只有**最后一条需清除信息被清除那一刻**才连带清空辅助状态、还原房间 |
| 6 | **重置不落任何消息**；提前 7 天提醒也不得落成系统消息（否则计时主体自续、永不到期） |
| 7 | `seq` 与 PIN 属**墓碑**：不得重置 `seq`、不得删 `room` 行、不得清 `pin_hmac` / `pin_salt` |
| 8 | 计时主体**只读 `messages`**；`last_active` / 辅助表行数都不得当判据（alarm 自己续写会自锁） |
| 9 | 清空事件**不是排程点**：某次 alarm 滚动 DELETE 后「由非空变空」，在**同一次 alarm 里**清辅助表、应用 B1–B3、`notified_clean=0`、不排新闹钟 |

**（2）三条还原规格**（详解见 G·8.2）

| | 口径 |
|---|---|
| **B1** | **PIN 保留**：`pin_hmac` / `pin_salt` 属墓碑，任何清理路径不得清除。代价是「全新房间」仍带锁 |
| **B2** | **`rule` 与 `baredice` 回默认**：还原时写 `rule='generic'`、`baredice=0`、清空 `rule_set_by/rule_set_at`。**这是重置动作本身的一步，不是用户发 `.set rule` 指令**；只改字段 ＋ `STATE` 帧同步顶栏，零消息 |
| **B3** | **累计接入人次归零**：清 `members` 即归零，**不加 `total_joins` 列** |

**（3）alarm 形态与五个实现坑**（详解见 G·8.5）

- 形态：逐条滚动 DELETE 只动 `messages`；「由非空变空」那一次才归零；半开连接巡检与 30 天清理同一次 alarm。
- 五个坑：① 重置路径写新消息 → 计时主体自续；② `last_active` 被 alarm 自己续写 → 房间永不清；③ 提醒落成系统消息 → 同上；④ 辅助表行数混进「是否仍有可清除信息」判据 → 空房间永不重置；⑤ 把辅助表挂进逐条 DELETE 的级联 → 战斗打到一半条目消失。

**（4）当前代码与设计口径的区别（如实登记）**：当前 S1 代码「清理 SQL 只删 `messages` 与 `idempotency`」「提前 7 天提醒确实落一条系统消息」是**现状事实**，不是功能开发轮设计口径；改造排期在功能开发轮。T6b 的四条守恒断言盯住**将来新增的「还原 / 重置」路径**（现在没有，全绿；将来谁实现时落消息就红），旧现状显式打印标注「不判红」，避免「全绿」被误读成「现状已合规」。

### 3.3 贯穿全程的方法论（详见 §4.1）

1. 诊断说正常但功能仍坏 → 先怀疑诊断没覆盖到坏的那条路径。
2. 验证「产出」必须跑真实入口函数，手搓 fixture 只能测「处理」。
3. 单测验的是规格，真机验的是场景；**本地全绿 ≠ 线上结构相同**。
4. 测试替身不能抄生产逻辑；单测盲区在胶水层；生成物与手工修改互斥。
5. 「新房间正常」不等于「老房间正常」；**断言自己也要被验证**。
6. 任何「看起来对的数字」都要能追到真实写入 / 真实行为。
7. **删代码前先问「谁把它当锚点」**；**接口对齐 ≠ 口径对齐**；**文案也是契约**。
8. 配置类改动别拿日志数字判通过；**想当然的状态码不是判据**（SPA fallback 会把「不存在」返回 200）。
9. 平台侧配置有「对象级状态」：删资源 ≠ 删引用，按「账户资源 → 生产绑定 → 模板 / Base → 已创建对象快照」四层逐个清。
10. 结构整理轮不改运行时行为；**扩张型优化只评估不实施**；方向 / 边界不确定先确认再落盘。

### A.5 COC 7th 规则包

#### A.5.0 属性（★ 2026-11-01 补：原来只有技能、没有属性，连体型 SIZ 都没注册）

**八大属性 + 幸运，全部按百分比存（1–99）**，与技能同值域、同检定链（都是 1d100 ≤ 数值），


### G·8.1 九条已定口径

| # | 口径 |

| 2 | 达到「30 天 或 消息续期时限，孰晚者」后，房间内**所有消息内容、辅助表格、访问记录一律清除** |

| 4 | **用户动作产生的 `notice` 留痕（导入完成、`.set rule` / `.set baredice` 提示等）计入计时**；任何用户主动动作都视作房间仍然存活 |

### G·8.3 模型速记

```
计时主体（自带寿命，参与「孰晚者」）
  messages 全 kind（含用户动作 notice 留痕）+ idempotency
  单条到期 = keep_until IS NULL ? ts + 30d : keep_until
  用户动作产出 ts=now 的新留痕、导出/导入续期一批 → 最后一条到期时刻不断后推
  ★ 「持续使用 / 持续导出 = 房间持续存活」自动成立

锚点（room 列，非执行指令）
  reset_at = max(计时主体里每条的到期时刻) ← 只由用户动作刷新，alarm 绝不写
  warned_for_reset_at ← 提醒对应哪个 reset_at，值变了才允许再提醒
  notified_clean ← 归 0 后可再触发

清空事件（不是排程点）
  某次 alarm 滚动 DELETE 后，若计时主体「由非空变为空」
  → 同一次 alarm 里清辅助表、应用 §8.2 还原规格、notified_clean=0、reset_at 置空、不排新闹钟

墓碑（永不清）
  room 行（code + created_at + pin_hmac + pin_salt）：撞号检测只读 created_at
  room.seq：不重置（msg_id = code:seq，压回 1..N 会撞已导出战报的 id → UNIQUE 报错 → 指令丢失）
```

分界线很干净：**进不进 `messages`、带不带 `ts` / `keep_until`**。提醒与重置都不进，不会伪装成用户动作；用户留痕进，天然算"房间还活着"。

### G·8.4 平实清单：重置那一刻具体发生什么

**先把两个容易混的东西分开**：

| | 用户发 `.set rule` / `.set baredice` | 重置时把规则/裸骰写回默认 |
|---|---|---|
| 是什么 | 用户主动指令，房间活着时随时可发 | **重置动作本身的一步**（B2，功能开发轮新增） |
| 聊天流 | 出现一条提示气泡（「由 老王 于 20:31 修改」） | **一条气泡都没有** |
| 数据库 | 写字段 **+ 落一条 `notice` 消息** | 只写字段回默认 / 清空设定者 |
| 对计时 | 新消息自带 30 天 → **房间续活** | **零影响** |
| 界面 | 顶栏规则名变化 + 聊天流多一条提示 | 顶栏规则名刷回默认，聊天流不动 |

**① 提前 7 天（提醒阶段）**：不产生消息、消息序号不跳；`room` 里记「这次警告对应哪个预计清空时间」防重复提醒；界面上进房/刷新时顶栏出横幅「本房间内容将在 X 后重置，重要战报请先导出」，在线的人可靠**不落库的瞬时帧**让横幅立刻出现。用户不管它 → 什么都不发生；用户点导出 → 给现有消息续 30 天，横幅消失、预计时间后推。

**② 重置那一刻**（最后一次删除把可清除信息删空）：

- **删掉**：所有消息、幂等记录、成员名单（昵称 / `cid` / 累计人次）、角色卡、未来的先攻表等全部辅助表。
- **改写（只是状态标记）**：`notified_clean=0`、`reset_at` 置空、累计人次归零；按 B2 写 `rule='generic'` / `baredice=0` / 清空设定者；按 B1 **PIN 字段不动**。
- **绝对不动**：房间号、创建时间、消息序号 `seq`、PIN。
- **绝对不做**：不插入任何消息、不 `allocSeq()`、不写 `last_active`、不调 `deleteAll()`（那会释放号码）、不排下一轮闹钟。
- **聊天流**：**一条气泡都不新增**，看不到「房间已重置」这句话。
- **界面（不落库）**：在线的人收到瞬时帧 → 旧消息列表清空、顶栏规则名刷回默认、人数归零、横幅消失；之后进来的人拿到空房间，`meta` / `.status` 里能看到「本房间已于 X 重置」——**读的是房间字段，不是聊天消息**。

**③ 重置之后**：老链接刷新进来就是空房间，名字、卡、历史都没了；谁发第一条消息，房间从那一刻重新开始 30 天计时（新一轮，不是上一轮续命）；一直没人发就一直空着、不排闹钟、不空转。

**④ 对照表**：

| 动作 | 产生消息？ | 让房间续活？ |
|---|---|---|
| 掷骰 / 聊天 / `.st` / `.set rule` / `.set baredice` / 导入战报 | **会** | **会** |
| 导出战报 | 不新增，但给现有消息续 30 天 | **会** |
| 提前 7 天提醒 | **不会**（横幅 / 瞬时帧） | 不会 |
| 房间重置本身 | **不会**（只改字段 + 同步界面） | 不会 |
| 纯访问 / 刷新 / 看到警告不动作 / 程序化扫房间 | **不会** | 不会 |

### G·8.5 alarm 的新形态与五个实现坑

500 MB 全局 KV 监测取消的是「跨 DO 容量巡检」，**不是 alarm**。`alarm()` 一直是每个房间自己的定时器：滚动 `DELETE`（S1 实测 DELETE 后磁盘立即回落）、`sweepIdle()` 关半开 ws、提前提醒（改瞬时）、以及新增的「计时主体归零时清辅助表」。完全删掉它，沉睡房间只能等下次访问才惰性清理，与口径 5 不符。

**有意义的容器** = 有在线 ws **或** 计时主体里还有未到期内容 **或** `reset_at` 未过。三者皆无 → **不排新闹钟**，DO 休眠等请求唤醒。有内容时取 `min(下次 idle 巡检, 下一条到期时刻, reset_at−7d, reset_at)` 作为**唯一**闹钟时间（每个 DO 同时只能有一个 alarm，`setAlarm()` 覆盖已有的）；**排到 `reset_at` 只为保证那次 `DELETE` 一定发生，是否还原仍以 `DELETE` 后 `COUNT=0` 为准**，不在时间点上无条件清空。重新 arm 只放在明确的用户请求路径（`join` / ws 握手 / 发指令 / `/export` / `/import`），并用 `getAlarm()` 判断是否已排、只在需要提前时覆盖；**构造函数里不许无条件 `setAlarm()`**（DO 休眠唤醒时构造函数先于 `alarm()` 执行，会干扰已排闹钟）。

| # | 坑 |
|---|---|
| 1 | **重置不能落消息**：新消息 `ts=now` 重新起算 30 天 → 计时主体永不归零 |
| 2 | **提醒不能落消息**：现 `alarm()` 把提醒写成 `kind:'sys'` 的 `messages` 行，`insertMsgs()` 不带 `keep_until`（默认 NULL）自带 30 天寿命；`/export` 续期 SQL 不排除 `sys`，按提醒去导出时提醒自己被再续 30 天 → 自续环 |
| 3 | **`notified_clean` 判定要重做**：现为 `now − created_at > 23d` 且只置一次；改成按 `reset_at − 7d`、每轮可再触发，文案改为「本房间内容将重置」 |
| 4 | **不调用 `deleteAll()`**：DO 写过 storage 后不自行消失，必须显式 `deleteAll()` 才停止计费/消失；但调它等于**释放号码**，与口径 1 冲突。**「停 alarm」≠ 销毁容器** |
| 5 | **★ `last_active` 不能当存活锚点**（代码实测）：全仓只有两处写它 —— ws 握手（`room.js` 第 498 行）与 **alarm 第 649 行每次都写 `now`**；`join` / `meta` / `/export` / `/import` 全都不写。拿它当判据，自我续期的 alarm 会让空房间**永远不重置**。必须另立 `reset_at`，且 alarm 绝不写 |

## I·2. 模块 A：属性生成

### I·2.1 定位与技术路线

- **定位**：独立小工具，生成数值串供玩家自行复制到 `.st`；**不读卡、不写卡、不改房间状态**。
- **动词**：`.coc` / `.dnd`，**全局动词，不绑 `room.rule`**。理由：输入项 A §1 决策快照「属性生成器小工具」、v5 §1「未来做独立小工具生成指令串」；绑规则会迫使车卡前先 `.set rule`，而切规则会触发 `@全体` 显著广播，平白刷全房警告。竞品（海豹 `.coc` / `.dnd`）亦为全局指令。
- **不泛化风险的处理**：`.coc` / `.dnd` 输出完全不依赖 `room.rule`，身份就是通用工具动词；与规则包的耦合仅限**静态数据引用**，不调用任何规则包行为接口（`runCheck` / `parseCard` / `renderCard` 均不用），不存在包间交叉调用。
- **数据归属（避免「横切决策只落实一处」漂移）**：
  - COC 属性顺序直接 import `coc.js` 的 `COC_ATTRS`（`力量 体质 体型 敏捷 外貌 智力 意志 教育 幸运`），与 `.st` 模板逐项一致 → 自动满足「呈现顺序与 .st 模板一致」，**不新增第三份手写数据**。
  - DND 标准数组为全新常量，只放 `dnd.js` 一处。
  - 主流程用一次 `GEN_SPEC[verb]` 查表，**不写 `if(verb==='coc')…else if(verb==='dnd')…` 分规则分支**（档案 A.8）。
- **不进 T6a 必选契约**：`check-rule-registry.js:92` 的 7 字段契约若加先攻/生成字段，会让 5 个 `pack_*.js` 全部补 `return null`，与「DH/FU 零增补」冲突。生成器数据按模块 import，不动契约。

### I·2.2 指令集

| 指令 | 语义 |
|---|---|
| `.coc` | 生成 1 组 COC 7th 属性 |
| `.coc <N>` | 生成 N 组 |
| `.dnd` | 标准数组 + 1 组随机（**裸命令口径，已确认**） |
| `.dnd <N>` | 标准数组 + N 组随机 |

- `<N>` 取值 **1–20**，两个命令同口径；写入 `.help coc` / `.help dnd`。
- `.coc 0` / `.coc 25` / `.coc abc` → **显式提示「组数 1–20」**，不静默截断、不兜底成 1（档案铁律：截断后的指令会掷出一个用户没点的结果）。
- **大小写不敏感**（动词归一化已 `toLowerCase`）。
- **无中文别名**（设计稿 `.生成`/`.造卡` 易与中文句号「。」误切；现有 verb 域只收 2 字以上中文动词）。
- **不支持回选 / 引用写卡**（`.gen take` 整条链路作废）；`.st` 只认玩家输入信息。
- `.coc` / `.dnd` 目前只存在于 `rules.js` 的 rule 域，与 verb 域独立；`card.js` verb 域现有 15 动词无 `coc`/`dnd`/`gen`，**不冲突**；新增仍须跑 `detectConflicts()`。

### I·2.3 COC 输出规格

- 属性顺序 = `.st` 模板顺序：`力量 体质 体型 敏捷 外貌 智力 意志 教育`，**幸运单列**。
- 只做 7 版基础公式：`STR/CON/DEX/APP/POW = 3d6×5`；`SIZ/INT/EDU = (2d6+6)×5`；`LUCK = 3d6×5`。
- 两个总和：**含幸运总和（九项）/ 不含幸运总和（＝八项基础属性之和）**（示例数值须自洽）。
- **COC 派生值（HP / MP / SAN 初始 / DB / 体格）一个都不出现**；体格表为 `coc.js` 的 `DB_BUILD` 内部数据，不面向玩家展示。玩家把属性贴进 `.st` 后，现有 `cocDerived()` 自会给出「复制一次录入」的指令（S1 真机已验）。「灵感/意志/幸运 ×5」是口径错误，已排除。
- 不做年龄修正 / 年代修正 / 6 版 / 经典变体；由玩家自己手动调整。
- **展示行 + 可复制行分离**：`.st set` 只认「名字 空格 数值」，冒号与 `|` 贴进去会解析失败，故单独给一行纯文本 `.st set`。该行仅为提示，**骰娘不代发、不二次解析**。`.st set` 是同族合并（`Object.assign({}, base, r.data)`），只覆盖同名属性、保留技能与背景。

示例（固定格式）：

```

1⃣ 力量:75 体质:50 体型:60 敏捷:55 外貌:60 智力:75 意志:70 教育:70 | 幸运:65 ➔ 总和 580 / 不含幸运 515

```

### I·2.4 DND 输出规格

- 只做 **4d6 弃最低 ×6**；结果 **6 个降序两位数（补零）**，**不对应属性科目**、不给名字、不给 `.st set`、不联动卡。理由：只给基础数值，玩家仍需自行分配与调整，车卡让玩家手动来。

- **每次回复首行固定是标准数组**（把它做成消息回复格式的一部分），其后才是随机 1、随机 2 …。
- 给合计衡量强度；**不做 27 点购点**（不处理 DND 车卡具体工作）。
- COC / DND 差异化是**刻意设计**（两套车卡流程天然不同），不做成对称结构。

## I·3. 模块 B：DND 先攻

> 全文统一书写为 `.init` / `.ri`；`.inti` 视为同一指令的笔误，不另立动词。

### I·3.1 规则归属机制

- **只有 DND 5e / 5.5e（`dnd5e` / `dnd5r`）需要先攻**；COC / DH / FU / **generic** 都不做，DH/FU 本阶段零增补。
- **采用：归属层复用现有机制 + 执行层在 Worker，不破例、不加必选契约字段。**
  - 归属/可用性：`verbOwner()`（`packs.js:17`）遍历 `RULE_PACKS`，谁有 `p.verbs[verb]` 归谁；`cmd.js:341–356` 已有 `.dh` / `.fu` 的「打错规则不静默，提示归属 + 怎么切过去」范式。`DND_PACK` 现无 `verbs` 字段，加一个即可；`dnd5e` 与 `dnd5r` 共用同一 `DND_PACK`，加一次两版本生效；`GENERIC_PACK` 不加即不支持。
  - 执行层：`.dh`/`.fu` 的规则包函数只返回 `{view}` / `{notice}`，引擎包成 `kind:'roll'` 消息即完事——引擎纯 ESM、零 DOM / 零 Node API，碰不到 DO storage。实际链路是 `core.js:128` 调 `Engine.handleCommand` 只拿 `msgs`，`room.js` 落库 + 广播。**先攻要写 `combat*`、要广播，必须在 Worker 层**。故 `DND_PACK.verbs.ri` 挂的是**声明 + 默认公式等静态数据**，不是执行函数。
  - 这不是破例：「专属动词」本就有纯计算型（引擎内闭环）与状态型（引擎判归属 → Worker 执行）两种。
  - 可选字段方案：在 `DND_PACK` 内部加**可选** `initiative` 声明，其余 4 包不写即表示不支持；Worker 用 `rulePack(room.rule).initiative` 查表，拿到放行、拿不到提示，**仍无分规则 if-else**，A.8 不破、T6a 契约断言不动、5 个包不动。
  - 顺带：`cmd.js:343` 的 `verb === 'dh' || verb === 'fu'` 硬编码需泛化成「按归属表取」，方向与 T3a/T6a 的「唯一实现」一致。
- **提示文案按族给「D&D 5e / 5.5e」两个目标**。原因：`verbOwner()` 按 `generic→dnd5e→dnd5r→coc7→dh→fu` 遍历，首个命中恒为 `dnd5e`，单值提示会让 5.5e 房看到指错版本的指引。
- 不采用的两条路径：契约必选字段 + 5 包返回 null（动契约 + 5 包 + 检查脚本，与「DH/FU 零增补」冲突）；主流程硬写 `if(rule==='dnd')`（违反 A.8）。

### I·3.2 一场战斗的生命周期

**状态判定**：不做持久化的「S2 冻结状态」，改用**运行时比对**——参考 `cardMismatchNote(card.js:60)` 的「卡与规则一致就可用、错配就提示」模型。每次先攻指令执行时用 `room.rule` 与先攻表的规则归属比对，一致就放行、错配就提示。表本身不清空、不改状态字段，切回 DND 自然恢复可用。

| 状态 | 定义 |
|---|---|
| **S0 空表 / 未开启** | `combat_entry` 无行 |
| **S1 战斗中** | 有条目，`combat` 行存在 |
| **S1' 规则错配（运行时）** | S1 且 `room.rule` 非 DND；表保留，指令冻结 |

**转换与反馈**：

| 触发 | 结果 | 反馈 |
|---|---|---|
| S0 + 首个 `.ri` 写入首个条目 | → S1 | **显著广播**：`⚔️ 先攻已开启` |
| S0 + `.init`（查询） | 保持 S0 | 普通消息：`当前未开启` |
| S1 + `.init`（查询） | 保持 S1 | 普通消息：状态「战斗中」+ **完整先攻序列** + **指针指明当前轮次**（未明确推进过时默认指向首位） |
| S1 + **`.init` 系列任意命令**（表仍非空） | 执行 + 保持 S1 | 普通消息：**当前先攻序列 + 回合指向** |
| S1 + **清空类命令**（`clear` / `combat <词>` / `战斗结束`，或 `del` 删到最后一个条目） | → S0 | **只发一条显著广播**「战斗结束，先攻表已清理」（可含「已清理 N 个条目」）；表已空，不再返回序列与指针 |
| S1 + **`.ri` 系列任意命令** | **新建条目，或同名条目覆写**（均同步确定先攻值） | 简短成功回执「已添加 老王 17」／「已更新 老王 17 → 21」；**战斗进行中另带顺位影响提示 + 完整序列 + 指针**（§3.4.3），战斗未开启的首个条目只回简短消息 + 开启广播 |
| 表由非空变空（任何指令路径） | → S0 | **显著广播**：`战斗结束，先攻表已清理` |
| S1 + `.set rule` 切到非 DND | → S1'（运行时判定） | 按 `.set rule` 自身口径广播；**不清空先攻表** |
| S1' + **`.init clear` / `.init combat <词>` / `.init 战斗结束`** | → S0 | **豁免放行**；按清空口径给广播 |
| S1' + 其余全部先攻相关指令 | 保持 S1' | **规则错配提示**，仿 `cardMismatchNote`：「这是 D&D 先攻表，当前规则「X」下不可用 —— 用 `.set rule dnd` / `.set rule dnd5r` 切回后恢复，或用 `.init clear` / `.init 战斗结束` 清理」 |
| S1' + 切回 DND | → S1 | 自然恢复可用，无需状态迁移、无需补消息 |

**错配豁免清单（已定）**：`clear`、`combat <词>` 与中文整串 `战斗结束` 三组（同一「结束整场」key，只是不同写法）。理由：`end`（推进回合）与 `del`（删条目）都是局部/单条目操作、不会清空整表，能够全局清理的只有这些；切回 DND 后按「一致就可用」正常放行。

**广播统一不变量（已定）**：

> **所有会导致先攻表在「空 ↔ 非空」两个状态之间变化的指令，都触发显著广播**；变化方向决定文案（空→非空 = `⚔️ 先攻已开启`，非空→空 = `战斗结束，先攻表已清理`）。

因此以下全部成立：

- `.ri` 首个条目 → 开启广播。**空→非空只能由 `.ri` 触发**（`.init set` 只编辑已有条目，见 §3.4）。
- `.init del` 删到最后一个条目 → 结束广播（与 `clear` / `combat end` 同款，判定条件唯一：`COUNT(combat_entry)` 由 >0 变 0）。
- 错配状态下的 `clear` / `combat end` → 同样给结束广播。
- 表内增删但不改变空/非空状态（如第 2→3 条、删 1 条剩 2 条）→ **不广播**，走普通消息。

**★ 唯一例外（必须写进实现与断言，见 §3.8）**：房间重置时的系统清表**不触发任何广播**。它不是「指令」，是输入项 A §8 的系统清理路径，按 L3 / §8.1-6 **零消息、零续活**。若在这里发广播，会直接把计时主体自续到永不到期——正是输入项 A §8.5 坑 1/2 的同型事故。

**结束整场战斗 / 推进一回合（已定）**：

| 指令组 | 语义 | 词表 |
|---|---|---|
| `.init <词>` | **推进一回合**（指针下移、不清表） | `end` / `finish` / `over` / `结束` / `next` / `下一位` |
| `.init combat <词>` | **结束整场战斗**并清空表 | `end` / `finish` / `over`（**`next`、`结束` 均已删除**） |
| **`.init 战斗结束`** | 同上，中文整串入口 | `战斗结束`（`战斗 结束` 带空格亦等价） |

- `combat next` **已删除**：`next` 在两个命名空间下语义相反，误打代价大，无代价消除风险。
- **`.init combat 结束` 已删除**：中文用户几乎不会打「combat + 中文词」的混搭，正式中文入口统一收敛到 `.init 战斗结束`。删除后 `combat` 词表只剩 3 个英文词，与推进词表的 `结束` **彻底无重叠**，误打风险再降一档。
- **★ 帮助必须写清的一对**：`.init 结束` = **推进一回合**；`.init 战斗结束` = **结束整场战斗**。两者靠整串精确匹配区分（实测 `normToken('战斗结束') !== normToken('结束')`），技术上不冲突，但对玩家是易混淆入口。
- 两组靠 `combat` 前缀区分命名空间，首词是 `combat` 就不会被 `end` 抢解析。
- `endcombat` 单 token **不再作为正式命令**。`normToken()` 会把 `combat end` 归一化成 `combatend`，而 `endcombat` 是 `endcombat`，**两者不同键**；若将来要兼容必须显式注册。

- **结束战斗 = 删除，不归档**：删 `combat_entry` 行与 `combat` 行；历史信息全在此前每条 `.init` 返回的「序列 + 指针」消息里，可回放、可导出。与 §8「辅助表无独立寿命」一致。
- **清空路径语义等价**：`.init combat <词>`、`.init 战斗结束`、`.init clear`、以及 `.init del` 删到最后一个条目，四者都执行「删 `combat_entry` + 删 `combat`」并给同一条结束广播；区别只在词表与玩家心智（「结束整场」vs「清空表」），实现不得做出差异。
- **指针 / 回合 / 回退边界（已定）**：
  - 删条目时若删的正是当前指针 → 指针指向排序中的下一位；删到空表则按「非空→空」给结束广播。
  - 推进走完一圈回到排序首位时 `round` +1；`.init prev` / `.回退` / `.上一位` 到首位即停，不倒扣 `round`。
  - **战斗进行中新增条目**：不调整 `cursor_entry_id`、不改变 `round`，**不做本轮指针动调整**；新增项按 `value` 插入排序。若排在指针之后，正常往下推进即可；若插入已行动区域（指针之前），可能本轮被跳过——反馈里提示「可能影响本轮行动顺位」，由玩家看完整序列**自行独立判断**并按需改值修正（§3.4.3 A 方案）。
  - 改值 / 覆写同理：指针跟着条目走、不指错人，顺位影响交给玩家判断。

### I·3.3 消息与广播分级

- **先攻体系内全部指令与反馈都落 `messages`**，`ts=now`、参与计时 → 按 §8.1-4 算用户动作，**房间续活、`reset_at` 后推**。
- **查看类也落消息**。
- **全员同权限可变更**（无 GM / 房主 / 权限字段）。用户口语里的「主持人创建怪物」只是角色扮演说法，**不引入任何权限实现**。
- **广播分级（已定）**：

| 级别 | 适用 | 通道 |
|---|---|---|
| **显著广播** | 仅「空→非空」与「非空→空」两条状态变化 | 复用 S1 `.set rule` 同款：`say({kind:'sys', title:'⚠️ @全体 …', line1, line2})`（`cmd.js:234`），大字号 / 警示色 / @全体 |
| **普通消息** | 其余全部指令与反馈（含 `.ri` 成功回执、`.init` 序列与指针、错配提示） | 复用现成 `notice()` → `kind:'notice'` |

- **补充口径（已定）**：
  1. 显著广播**不额外再发一条状态消息**——「空↔非空」变化只用一条 `sys` 显著广播承载，不再补一条普通消息复述同一状态变化，避免双发刷屏。它与**操作回执**是两回事：首个 `.ri` 仍有一条 `notice` 回执「已添加 A 17」，加上一条 `sys` 开启广播；两条用途不同、都落 `messages`，不算双发。
  2. `⚔️` 前缀 + `@全体` 走 `sys` 的 `title/line1/line2` 三字段（`renderSys` 是**纯文本**通道，`cmd.js:240` 明确不能带 `<b>`），**不新增 kind、不改 payload 白名单、不动快照**。
  3. `.ri` 回执带条目名与值（「已添加 老王 17」／「已更新 老王 17 → 21」），多人同时 `.ri` 时分得清谁加的。
  4. 输入项 A §8.5 坑 2 的「`sys` 消息被 `/export` 续期形成自续环」只针对**系统自发提醒**；先攻留痕是用户主动动作，被续期**允许且符合预期**，两者不混。

### I·3.4 指令集框架

#### 分工定稿：按名字 upsert vs「安全编辑」

**分工定稿**：`.ri` = **按名字 upsert + 同步确定先攻值**（存在覆写 / 不存在新建，始终掷骰或定值，不设子命令前缀）；`.init set` = **只编辑已有条目**（名字不存在明确报错）。两者功能重叠处保留**有意的不对称**，因为「录入 / 重录」与「编辑一个确定存在的单位」在玩家心智与实操里是两件事，不因功能重叠而合并成一个入口；该不对称必须写进帮助。

| 指令 | 名字不存在时 | 玩家心智 | 用途 |
|---|---|---|---|
| `.ri 老王 +2` | **新建条目**（可能触发空→非空开启广播） | 「录入 / 重录」 | 开战录入 / 重录 / 批量建怪 |
| `.init set 老王 18` | **明确报错**「条目不存在，用 `.ri` 创建」 | 「编辑已存在的单位」 | 战斗中改值，防拼错名字造条目 |

| 组 | 职责 | 明确不做 |
|---|---|---|
| **`.ri`** | 按名字 upsert + **同步确定先攻值**（掷骰或固定值，一步完成）；**不设任何子命令前缀** | 不删、不推进、不清表、不提供 `.ri set` 这类不掷骰的专门入口 |
| **`.init` = R/U/D** | 查看序列 + 指针、推进/回退、**改已有条目的值（可同步重掷）**、删条目、清表、结束整场 | **不创建新条目**（名字不存在 → 报错） |

> **广播判定不受影响**：空→非空**只可能由 `.ri` 新建触发**；`.ri` 覆写与 `.init set` 都不改变空/非空状态 → 不广播。状态机仍只有一个入口。

> **★ `add` / `添加` 整组取消**：它们原本是 upsert 别名，语义是「增加条目」；`.ri` 天然带这个语义，挂到「只编辑」的 `.init` 上会误导用户。`.init set` 的别名只用 `set` / `设定` / `改` / `修改`。

#### `.init` 家族（R/U/D）

| 指令 | 语义 | 状态 | 别名 |
|---|---|---|---|
| `.init` | 查看当前表 | 已定 | **`.先攻表`**（只收这一个） |
| `.init set <名> <值>` | **编辑已有条目的值**：固定值（不掷）或表达式/调整 + 优劣势（**同步重掷**）；名字不存在 → 报错 | 已定 | `set` / `设定` / `改` / `修改` |
| `.init del <名>`（含批量） | 删条目；删到空 → 结束广播 | 已定 | `del` / `删除` / `移除` |
| `.init clear` | 清空整表 → 结束广播 | 已定 | `clr` / `清空` / `清除` |
| `.init combat <词>` | **结束整场战斗**并清空表 → 结束广播 | 已定 | `<词>` ∈ `end` / `finish` / `over`（`next` 与中文 `结束` 均不在词表内） |
| **`.init 战斗结束`** | **同上，正式中文结束入口** | 已定 | `战斗结束`（`.init 战斗 结束` 带空格亦等价） |
| `.init <词>` | **推进一回合**（指针下移、不清表） | 已定 | `end` / `finish` / `over` / `结束` / `next` / **`下一位`** |
| `.init prev` | 回退一个回合（到首位停、不倒扣 `round`） | 已定 | `prev` / `回退` / `上一位` |
| ~~`.init first`~~ | ~~破并列手动提前~~ | **砍掉** | — |

> **★ 易混淆的一对，帮助里必须写清楚**：`.init 结束` = **推进一回合**；`.init 战斗结束` = **结束整场战斗**。两者靠整串精确匹配区分（实测 `normToken('战斗结束') !== normToken('结束')`，见 §3.4.1），技术上不冲突，但对玩家是易误打的一对。

**`.init set` 的实现口径**：

- 复用 `.ri` 三段解析器里的**值段与优劣势段**（去掉角色/批量段），成本极低，也正好实现「基于具体指令段支持同步投掷」。
- 覆盖 `value` 后 **`id` 与 `created_at` 保持不变** → 「先入者优先」，同值排序不因改值而跳位（见 §3.4.3）。
- 重掷时敏捷调整值快照沿用条目原有 `card_ref`（见 §3.6）；无卡 / 卡上无数 / 他人 / 怪物 → 0。
- 错配状态下 `.init set` **不清空表 → 不豁免**，照常返回错配提示。
- 不改变空/非空状态 → **不触发显著广播**，走普通消息；但**要带顺位影响提示 + 完整序列 + 指针**（§3.4.3）。

#### `.ri` 家族（按名字 upsert）

`.ri` **不设任何子命令前缀**，全部由三段标记位表达；同名覆写与新建共用同一套值段解析。详见 §3.4.2。

**回执形态**：

| 情形 | 回执 |
|---|---|
| 新建（战斗未开启，含批量作为首批条目） | `notice`「已添加 老王 17」／批量「已添加 哥布林1 14、…」+ **一条** `sys` 显著广播「⚔️ 先攻已开启」；无顺位提示、无序列 |
| 新建（战斗进行中，含批量） | `notice` 简短回执 + 顺位影响提示 + 完整序列 + 指针 |
| **同名覆写** | `notice`「已更新 老王 17 → 21」+ 顺位影响提示 + 完整序列 + 指针 |

### I·3.4.1 子命令解析（技术结论）

**结论：`combat <词>` 两段式让解析顺序的坑自然消失，中文整串别名也不引入新坑；无需改动 `parseCommand()` 主流程。**

- `parseCommand()`（`cmd.js:29–49`）只把输入切成 `verb` + `rest`，`rest` 是一整串自由文本；子命令解析在各自分支内手写。现有先例：`.st set 力量 60` 用 `a.match(/^set\s+(.*)$/i)`（`cmd.js:315`）、`.set baredice on` 切首词 + 余参、`.st list` 直接整串比较（`cmd.js:288`）。
- `.init combat end` 首词是 `combat`，推进词表里没有 `combat` → 切首词就能分派，不会被 `end` 抢走。
- **解析顺序**：先**整串精确查** `initcmd` 域（吃掉 `战斗结束` / `结束` / `下一位` / `clear` / `clr` / `清空` 等无参单 token），整串没命中再**切首词**处理带参子命令（`set 老王 18` / `del 哥布林1`）与 `combat <词>` 两段式。因为 `lookupAlias()` 是 `normToken` 后的**精确 Map 匹配**、不是前缀匹配，所以 `战斗结束` 与 `结束` 是两个独立键，天然不互抢。
- `normToken()`（`alias.js:7`）会 `.replace(/[\s_]/g, '')` 去掉空格与下划线。沙盒实测：

  | 输入 | 归一化 | 结论 |
  |---|---|---|
  | `战斗结束` / `战斗 结束` | 均为 `战斗结束` | 两种写法**免费等价** |
  | `结束` | `结束` | 与 `战斗结束` 不同键 ✓ |
  | `combat end` / `combatend` | 均为 `combatend` | 中文无关 |
  | `endcombat` | `endcombat` | 与 `combatend` **不同键**，兼容须显式注册（不注册即不合法） |

- **中文动词最长前缀匹配实测**：`CJK_VERBS` 由 verb 域生成并按长度降序（`cmd.js:22–27`）。注册 `.先攻`(→`ri`) 与 `.先攻表`(→`init`) 后：

  | 输入 | 命中 | rest |
  |---|---|---|
  | `.先攻表` | `init` | 空 |
  | `.先攻 +2` | `ri` | `+2` |
  | `.先攻老王 +2` | `ri` | `老王 +2` |
  | `.先攻表 set 老王 18` | `init` | `set 老王 18` |
  | **`.先攻表哥 +2`** | **`init`（被「先攻表」抢走）** | `哥 +2` |

  > **★ 边角歧义（已接受、不特判）**：角色名若以「表」字开头（如「表哥」），`.先攻表哥` 会被 `.先攻表` 抢走（rest 变 `哥 +2`）。这是中文动词最长前缀匹配的固有边界；建议玩家用 `.ri`/`.init` 或 `@"表哥"` 规避。补充观察：名字里若带空格（如「表 哥」）会被切成多 token，反而走显式报错或双引号路径，**不会静默误判**，实际风险比无空格时更低。写进验收断言与帮助，见 §3.9 第 13 条。

- **别名冲突自查（真实引擎实测）**：在完整引擎上跑 `detectConflicts('verb', [先攻, 先攻表, 理智, 死豁, 死亡豁免, 下一位, 战斗结束])` 返回 `[]`；verb 域这些键当前均为 `null`，`check:*` / `cardkey:*` / `mode` / `switch` 域也没有同名项。COC 的 `COC_ATTRS` / `COC_SKILLS` 里没有「理智」（备忘字段是 `san`），所以 `.理智` 作动词别名不会与「理智检定」的认知冲突。
- **优劣势参数**：`优势` / `劣势` / `有利` / `不利` / `优` / `劣` 都在 **`mode` 域**（实测 10 个键），与 verb 域里 `ra`/`rd` 的同名别名**分域独立、互不干扰**；`.ri` 参数解析复用 `cmd.js:120–124` 的 `lookupAlias('mode', token)`，与 `.r 1d20+5 优势` 同源。
- 别名注册须同步 `cmd.js` 的 `VERBS` 集合 + `card.js` 的 verb 域 + `detectConflicts()`；子命令别名建议新建 alias 域（`initcmd` / `combatsub`），避免与 verb / mode / switch 域串味。

### I·3.4.2 `.ri` 整体格式

**核查到的硬约束（沙盒实跑 `parseExpr()` 验证）**：

| 输入 | `parseExpr()` 结果 | 含义 |
|---|---|---|
| `d20+d8` / `d20+2` / `2d20` / `1d20+1d4` / `d8+3` | **ok** | 完整表达式合法 |
| `+1d8` | **ok** | 单骰组带 `+` 前缀合法 |
| **`+2` / `-1` / `18`** | **失败 `syntax`** | **`groups.length === 0` 被拒**；`parse.js:23` 要求至少一颗骰 |
| `-1d4` | 失败 | 负骰组被 `parse.js:27` 拒 |
| `3#哥布林` / `@老王` / `张三` | 失败 | 非表达式，天然可与值段区分 |
| 拼成 `d20+2` / `d20-1` / `d20+1d4`（敏捷调整值取 0 时） | **ok** | 「调整项叠加到默认公式」的实现路径 |

> **★ 这个实测结果直接支撑了格式设计**：纯调整值 `+2`、固定值 `18` **本来就不是合法表达式**，所以「叠加到默认公式 `d20 + 敏捷调整值`」不是宽容处理，而是**必须**先拼成一条含 d20 的表达式再交给 `parseExpr()`；「纯数字 = 固定值，不掷骰」也因此与表达式天然分道，**不存在歧义判定成本**。

**格式定案**：

```
.ri  [角色]  [值/表达式]  [优劣势]        ← 三段顺序任意，各自独立识别
```

| token 形态 | 归类 | 语义 |
|---|---|---|
| **无角色标记** | 角色 = 投掷者自身 | 条目 `name = 当前昵称` |
| `@名字` | 角色（**`@` 可选前缀**） | 单个具名单位；`@老王` 与裸写 `老王` 等价 |
| `N#名字` | 角色 + 批量（**绑定**） | 创建 N 个条目，自动编号 `名字1…名字N` |
| `d20+d8` / `2d20` / `1d20+1d4` / `d8+3` | **完整表达式 → 整体覆盖默认** | 直接喂 `parseExpr()`，**不需要 `=` 号** |
| `=d20+3` | 同上的显式写法 | **可选**，仅照顾习惯，非必需；可与调整项合并 |
| `+2` / `-1` / `+1d4` | **调整项 → 叠加到默认公式 `d20 + 敏捷调整值`** | 按「基底在前、调整在后」定序拼成 `d20+<敏捷>+2` 等再 parse；敏捷取 0 时即 `d20+2` |
| `-NdM`（负骰组，如 `-1d4`） | **非法 → 显式报错** | 实测：`-1d4` 与 `d20-1d4` 均被 `parseExpr()` 拒；提示改用常数负值 `-1` 或完整表达式 |
| `18`（纯数字） | **固定值 → 不掷骰** | `value = 18`，不进 `parseExpr()`、不含默认敏捷项；`dex_mod` 仍按角色取快照作破平键 |
| `adv` / `dis` / `优势` / `劣势` | 优劣势 mode | 传给 `rollGroups(groups, mode, ruleKey)`，**整条指令连投两次取高/低**（不是只 d20 取高） |
| **剩余的那个 token** | **角色名**（裸名，无需 `@`） | 先识别掉上述所有已知形态，**剩下的唯一 token 即名字** → 顺序真正无关 |

**格式要点**：

**① `@` 前缀可省略**
`#` 本身已是标记、`@` 只是让「这是个人名」更醒目，二者都可省略：

- `.ri @老王 +2` ≡ `.ri 老王 +2` → 创建 **1 个**条目
- `.ri 3#哥布林 +2` → 创建 **3 个**条目 `哥布林1 / 哥布林2 / 哥布林3`

解析规则统一成「**已知形态先吃掉，剩下的唯一 token 即角色名**」，裸名与 `@名` 走同一条路径。

**② 两种写法创建的条目**

| 指令 | 条目数 | `name` | `owner` | `card_ref` | `value` | `dex_mod`（隐藏破平键） |
|---|---|---|---|---|---|---|
| `.ri @老王 +2` | 1 | `老王` | `老王` | **NULL** | `d20+2` 的掷骰结果（拿不到对方卡 → 敏捷调整值取 0） | **0** |
| `.ri 老王 +2` | 1 | 同上（完全等价） | 同上 | 同上 | 同上 | 同上 |
| `.ri 3#哥布林 +2` | 3 | `哥布林1/2/3` | **投掷者**（谁建的怪归谁，便于留痕） | NULL | 各自 `d20+2` 的独立结果（敏捷调整值 0） | 0 |
| `.ri +2`（无角色） | 1 | 投掷者昵称 | 投掷者 | **投掷者自己的卡**（若绑卡） | **`d20 + 敏捷调整值 + 2`** | `cardMod(card,'dex')`，无卡 / 卡上无数 → 0 |
| `.ri 18` | 1 | 投掷者昵称 | 投掷者 | 自己的卡（若绑卡） | 固定 **18**（不含默认敏捷项） | `cardMod(card,'dex')`，无卡 / 卡上无数 → 0 |

> **★ 敏捷调整值：默认公式的常数项 + 独立的隐藏破平要素**
>
> 记 `dexMod` = 从 `card_ref` 指向的角色卡读出的敏捷调整值；**读得到就用卡上的值（可为负），无卡、卡上没有该数值、或条目指向他人/怪物（拿不到对方卡）时取 0**。它承担两个互不重叠的职责：
>
> 1. **参与先攻值计算（默认公式 = `d20 + dexMod`）**：只有调整项、没有显式表达式基底时，调整项按 §3.4.2 ④「基底在前、调整在后」拼在默认公式之后，如敏捷 +3 时 `.ri +2` → `d20+3+2`、`.ri +1d4` → `d20+3+1d4`；`dexMod = 0` 时退化为 `d20+2` / `d20+1d4`。**完整表达式（`.ri d20+d8` / `.ri =d20+3`）整体覆盖默认公式**，本次 `value` 不含默认敏捷项，调整项改为拼在该显式基底之后（`=d20+3 +2` → `d20+3+2`）。固定值（`.ri 18`）不掷骰、`value = 18`，同样不含。
> 2. **单独存成隐藏字段 `combat_entry.dex_mod`**：值与 `dexMod` 同源同值，但**只用于 `value` 相同时的破平排序（第二键），不对玩家显示、不重复计入 `value`**。即先攻值里已经算过一次敏捷，同分时再比敏捷是「固有属性比较」，不是把敏捷算两遍。
> 3. **符号规范化（实现必需）**：`dexMod` 作为常数项拼进表达式时须按符号写成 `+N` / `-N` / 省略，**不得出现 `+-N`**。沙盒实测 `parseExpr('d20+-1')` 与 `parseExpr('d20+-1+2')` 均返回 `syntax` 失败，而 `d20-1`（mod = −1）、`d20-1+2`（mod = +1）正常解析。故敏捷调整值为负（如 −1）的默认公式必须拼成 `d20-1`，不能拼成 `d20+-1`；该规范化同样适用于 `.init set` 重掷与 `.ri` 同名覆写。
>
> 因此：**完整表达式 / 固定值路径下 `dex_mod` 仍按角色取快照并保留**，用于后续同值破平；`.init set` 重掷、`.ri` 同名覆写均沿用条目已存的 `card_ref` 快照，不因改值重取。他人 / 怪物条目两处均为 0。
>
> **措辞要点**：「`dex_mod` 字段不重复计入 `value`」≠「敏捷调整值不进先攻值」——前者说的是字段用途，后者说的是默认公式；两者不矛盾。

> **★ 必须说清的技术约束**：`core.js:39–41` 的 `buildCtx(anonId, nick)` 只调 `storage.getCard(anonId)` 取**当前用户自己的卡**；`pcs` 表按 `anon_id` 存（`room.js:65`），**引擎 ctx 里拿不到别人的卡**。所以 `@老王` / `N#怪` 这类「为他人/怪物创建」的条目，`card_ref` 恒为 NULL：默认公式里的敏捷调整值取 0（退化为纯 `d20` 加调整项），隐藏 `dex_mod` 也恒为 0。这不是设计选择，是现有架构的边界；若将来要支持，得改 `buildCtx` 注入全房卡索引，属跨模块改动，本阶段不做（已列入 S2 边界第 16 项）。
> 附带影响：同值时 NPC/他人条目 `dex_mod=0`，PC 若敏捷调整值高会排前面——这个结果合理且可接受。

**③ 完整表达式无需 `=` 号**
`.ri d20+d8` 定为正式写法，`d20+d8` 实测是合法表达式。区分规则不用 `=` 号，改看 **token 首字符**：

- 以 `d` / 数字开头且含骰组 → **完整表达式，整体覆盖默认**（`.ri d20+d8`、`.ri 2d20`、`.ri 1d20+1d4`）
- 以 `+` / `-` 开头 → **调整项，叠加到默认公式 `d20 + 敏捷调整值`**（`.ri +2` → `d20+敏捷+2`；`.ri +1d4` → `d20+敏捷+1d4`）
- 纯数字 → **固定值，不掷骰**（`.ri 18`）

`=d20+3` 仅作为可选的显式覆盖写法保留（照顾竞品习惯），**不是必需**。注意 **`d20+2`（完整表达式，整体覆盖默认）与 `+2`（调整项，叠加到默认公式）在有卡且敏捷调整值非 0 时结果不同**：前者不含默认敏捷项、后者含；只有敏捷调整值取 0（无卡 / 卡上无数 / 他人条目）时两者才一致。这不是歧义，是两条不同路径的必然结果，帮助里写明即可。另提醒：`.ri d8+3` 这类不含 d20 的表达式合法但先攻值会偏低，用户自己写的，不静默纠正。

**④ 表达式与调整项同现：合并成连贯公式**

**结论：不是空格问题，是「语义冲突」与「拼接顺序」两件事；合并成一条连贯公式是唯一答案。**

- 空格完全不是障碍：`parseExpr()` 第 8 行自己就 `.replace(/\s+/g,'')` 去掉所有空格；`.ri` 的 rest 本来就是按空格切好的独立 token。
- 合并方案的基底是用户显式给出的完整表达式，**不含默认敏捷项**；`=d20+3 +2` → `d20+3+2` → **1d20 + 5**。（若只有调整项、没有显式基底，则基底取默认公式 `d20 + 敏捷调整值`，见 §3.4.2 格式定案表。）
- **沙盒实测（`parseExpr()` 直接跑）**：

  | 合并结果 | 解析 |
  |---|---|
  | `d20+3+2` | ok，1d20、mod=5 |
  | `d20+2-1+1d4` | ok，1d20+1d4、mod=1 |
  | `2d20+1d4` | ok，2 组骰 |
  | `d20+d8-1` | ok，mod=−1 |
  | **`+2d20+3`（按输入顺序硬拼，错误做法）** | **ok 但变成 2 颗 d20 + 3** —— `+2` 的「2」被 `ITEM_RE` 吃成骰数！ |

- **★ 因此实现要点不是「改 parseExpr」（零改动），而是「分类收集后再定序拼接」**：先识别并分出「表达式基底」与「若干调整项」，按 **基底在前、调整在后** 拼成一条字符串，再一次性交给 `parseExpr()`；解析失败才报错。若按输入顺序 `join` 会静默掷错（上面最后一行），这正是必须显式定序的原因。
- **结论**：`=表达式` / 完整表达式 / 多个 `+/-` 调整项**同类合并**；负骰组与固定值混入仍报错。固定值 `18` 与表达式同现保持报错——因为它是「不掷骰」语义，与「掷骰」本质冲突，不属于同类合并。
- **★ 澄清「语序风险」的实际边界**：`+2d20+3` 那个反例**已被「分类收集 → 基底在前、调整在后」定序拼接规避**，不是留给用户的坑。剩下的边缘只是「用户自己写出 `d20+2d20` 这类本身合法但语义奇特的表达式」——属于用户自担、不静默纠正，与 `.ri d8+3` 先攻值偏低同款处理。

**⑤ 三段顺序无关**
三段各自独立识别：`+1d4` → 叠加成 `d20+敏捷调整值+1d4`（`张三` 为他人条目，敏捷取 0 → `d20+1d4`）；`adv` → mode = adv；`张三` → 剩余 token 即角色名。两者都**新建（或同名覆写，见 ⑩）** 1 个条目 `张三`，`value = (d20+1d4) 整条连投两次取高`，`dex_mod = 0`（他人条目），`owner = 张三`。

注意 `adv` 在 `rollGroups()` 里是**整条指令连投两次取高**，所以取高的是 `d20+1d4` 的合计值，不是只把 d20 取高；这与 D&D 标准优势先攻一致，也复用了 830 项断言守着的实现。

**⑥ 批量数量必须与角色字段绑定**：纯数字 token 已被「固定值」占用，`.ri 3 哥布林` 里的 `3` 会被当成先攻值 3。`3#哥布林` 一眼可判，与竞品（`N#怪名`）一致，别名不用重新教。

**⑦ 批量每个条目独立掷骰**：`3#哥布林` 调 3 次独立 RNG；`adv` 时每个条目各投两次取高。**不提供「共享一个值」的简写**。

> **★ 独立掷骰带出的排序键修正**：`3#哥布林` 在同一毫秒内建 3 行，若排序第三键用 `created_at ASC`，三行时间戳相同 → 排序不稳定（隐式依赖 rowid）。故**第三排序键改用 `combat_entry.id ASC`**：`id` 是 `INTEGER PRIMARY KEY` 自增、天然唯一且严格递增，语义仍精确对应「先完成 `.ri` 的排在前面」。`created_at` 保留作留痕/展示字段，不参与排序。见 §3.6。

**⑧ 裸名带空格的限制**：`@"哥布林 弓手"` 用双引号包裹；不带引号的含空格名字会被切成多个 token → **显式提示用法，不静默降级**。名字不能长得像表达式（如叫 `d20`），属不合理命名，不特判。

**⑨ 固定值算不算「投掷」**：本文把 `.ri` 的动作统一表述为「**新建或覆写条目 + 确定先攻值**」，固定值是「确定值」的一种方式，不额外掷骰；这样「两个动作同步」的定义成立，不必为固定值开例外。

**⑩ 同名覆写**：许可。`.ri` 按 `name` 匹配：存在 → 更新 `value` 并在回执标记旧值→新值；不存在 → 新建。

- 存在 → 更新 `value`（敏捷调整值快照沿用条目已存的 `card_ref`）、`id` / `created_at` / `owner` / `card_ref` **保持不变**；不存在 → 新建。
- **回执标记旧值 → 新值**：新增回「已添加 老王 17」，覆写回「已更新 老王 17 → 21」。仍是普通消息（不显著广播）。
- **`name` 在单场战斗内按唯一处理**：`N#怪` 自动编号天然不重名；若两人同名，后录入者覆写前者，帮助里写明这一口径（不做同名歧义消解，避免引入权限/身份字段）。
- 覆写**不改变空/非空状态** → 不触发开启/结束广播；但**要带顺位影响提示**（§3.4.3，与 `.init set` 同款）。
- 覆写与 `.init set` 的差别只在「名字不存在时」：前者新建、后者报错。这是 §3.4 有意保留的不对称。

### I·3.4.3 改值 / 新增影响顺位时的处理

**指针不会指错人**：`cursor_entry_id` 指向的是 `combat_entry.id`（**条目引用**），不是「排序下标」或「第几个」。所以条目因改值重排时，指针始终跟着条目走——这是双表 + id 引用相比单表 JSON 下标的核心优势（§3.5.1）。

**真问题**是：动态 `ORDER BY value DESC` + 单指针模型下，改 `value` 会让「指针之前 / 之后」的集合变化，于是可能出现「本轮已行动的单位降值后排到指针后面 → 本轮再动一次」或「未行动的单位升值后排到指针前面 → 本轮被跳过」。

**三个方案对比**（定案：A）：

| | **A 提示（已定）** | B 加 `acted_this_round` 字段 | C 回合内冻结顺序快照 |
|---|---|---|---|
| 做法 | 改值/覆写后，反馈里带一句「⚠️ 先攻值变化可能影响本轮行动顺序，请留意当前轮次」+ 本就有的完整序列与指针 | 每条目加布尔标记，推进时置位、走完一圈清空，指针按「未完成的最小顺位」推进 | 战斗开启时冻结一份顺序，回合内按快照推进，改值只影响显示 |
| 正确性 | 靠玩家判断 | 严格自动 | 严格但改值当轮不生效 |
| 新增状态 | **无** | 1 列 + 状态机 | 1 份快照 |
| 与项目哲学 | **一致**（HP / SAN / 死亡豁免都不自动追踪，骰娘只给事实与提示） | 有张力（虽非资源，但属自动追踪） | 不一致（消息即事实） |
| 老房间迁移 | 零影响 | 新表可一次带上，但仍多一处断言 | 多一份数据 |

**定案：选 A 方案**。依据与具体机制：

1. **与项目定位一致**：整个项目「骰娘不做动态追踪、玩家自己负责」（HP 不自动增减、SAN 不追踪、死亡豁免不记数）；A 方案只是给事实和提示，零字段、零迁移、零新断言。
2. **每条 `.init` 本来就返回完整序列 + 指针**，玩家有足够信息判断，不需要新增隐藏状态。
3. **★ 回退情境是 B 方案的真正软肋**：`acted_this_round` 不是孤立布尔值，而是要跟 `.init prev`、走完一圈清空、改值重排三者联动的状态机 —— 回退时要撤销标记；但「回退到谁」在排序已因改值变化后**本身就不唯一**（按旧顺序回退还是按新顺序？）。组合一多就容易出现「某人被跳过 / 多动一次」且**从外部看不出原因**。
4. **★ 更关键的是可观测性与可修复性**：A 方案下所有事实都在消息里（完整序列 + 指针 + 顺位提示），一旦玩家觉得顺位不对，直接发 `.ri` 覆写或 `.init set` 改值就能修正，聊天记录里也留得住；B 方案的 `acted` 标记藏在表里、消息里看不到，也没有任何指令能直接修这个标记，出错后往往只能 `.init clear` 重开 —— **人工调整成本反而更高**。这与「消息即事实」「存骰点不存结论」是同一条原则。

> 结论：A 方案不只是「心智成本最低」，也是「出错后最容易靠人工补救」的方案。若将来真机反馈「玩家经常漏看提示」，再评估升级 B，届时会明确告知新增字段、状态机与迁移成本。

**A 方案的落地口径（写进验收）**：

- **改值不改变 `cursor_entry_id`**：当前正在行动的单位指针不因重排而移动，「当前轮到谁」始终稳定。
- **改值不触发 `round` 变化**：`round` 只在指针走完一圈回到排序首位时 +1（删当前指针 → 指向下一位，走完一圈 +1，`prev` 到首位停），与改值无关。
- `.init set`、`.ri` 同名覆写、**以及战斗进行中的 `.ri` 新建**，都在回执里带那句顺位影响提示 + 完整序列 + 指针；**战斗未开启的首个 `.ri` 不带提示**（此时无「本轮顺位」可影响）。
- **新增条目不纳入本轮指针调整**：不改 `cursor_entry_id`、不改 `round`、不自动补正。新增项按 `value` 插入排序；若排在指针之后，顺序往下走即可；若插入已行动区域（指针之前），可能本轮被跳过——由玩家看完整序列**自行独立判断**，按需 `.ri` 覆写或 `.init set` 改值修正。
- 不新增 `acted` 字段、不做自动补正 —— 已列入 S2「仍然不做」第 17 项。

### I·3.5 数据模型

按设计稿 §2.3 新增两张表（**纯新增、不动老表列**）。

| 字段 | 含义 | 决议 |
|---|---|---|
| `side`（`pc/ally/enemy/neutral`） | 阵营标记，列表里区分 PC / NPC | **砍**：未要求阵营分组，且「不引入权限字段」 |
| `owner_anon_id` | 条目归属的真实成员 id；NPC 为空 | **简化为 `owner` 昵称文本**；消息里已有 `from`/`actor` 留痕。`@他人` → `owner=该名字`；`N#怪` → `owner=投掷者` |
| `card_ref` | 绑定的角色卡引用，用于读取敏捷调整值 | **留，但只能指向投掷者自己的卡**（`buildCtx` 边界）；他人/怪条目为 NULL，敏捷调整值取 0。只在录入当下取快照，不做实时联动 |
| `tie_break` | 并列时的显式权重，供 `.init first` 提前 | **砍** |
| `dice`（逐骰明细 JSON） | 记录 `d20` 原始点数、表达式、调整值 | **砍** |
| `expr`（原始输入） | 保存用户写了什么 | **不留**：与「不存逐骰明细」口径一致 |
| `dex_mod` | 敏捷调整值快照，后台写入、**不对玩家显示**，用于同值排序破平 | **留**：与默认公式里的敏捷调整值同源同值（读卡得到，无卡 / 卡上无数 / 他人 / 怪物 → 0），但**只作 `value` 相同时的第二排序键，不重复计入 `value`**；创建时按 `card_ref` 取一次快照存下来，与本次用完整表达式 / 调整项 / 固定值无关 |

**定稿结构（双表）**：

```
combat        : id, room_code, round, cursor_entry_id, started_at, started_by
combat_entry  : id(INTEGER PRIMARY KEY 自增), combat_id, name, owner, card_ref,
                value(排序值), dex_mod(隐藏), created_at, created_by
```

- **不挂 HP 字段**：纯顺序表，只有名字与先攻值；与「不做动态资源追踪」一致。
- `cursor_entry_id` 外键语义指向 `combat_entry.id`，是「当前轮到谁」的唯一当前值。
- `id` 同时承担排序第三键（§3.4.2 ⑦）。

### I·3.5.1 单表 vs 双表决策依据

| | **A 双表（已选）** | B 单表 + JSON 数组 | C 单表平铺 |
|---|---|---|---|
| 结构 | `combat`(1行/房) + `combat_entry`(N行) | 一张 `combat`：`round`/`cursor`/`entries` JSON | 一张 `combat`(N行)：战斗级字段每行重复，或插 `__meta__` 行 |
| 唯一当前值 | `cursor_entry_id` 外键，天然唯一 | 指针是数组下标/名字，改名/删条目后易悬空 | 改指针要 UPDATE 全表 = N 个副本 |
| 排序 | 一条 `ORDER BY value DESC, dex_mod DESC, id ASC` | 在 JS 里排整个数组 | 能排，但要先 `WHERE` 过滤 meta 行 |
| 并发写 | 插一行 / 改一列，互不覆盖 | 每次变更整段 JSON 覆盖 | 改指针要写 N 行 |
| 清空 | 两行 DELETE（需成对，见 §3.8 C2） | 一行 DELETE | 全表 DELETE |
| 老房间迁移 | 2 次 `CREATE TABLE IF NOT EXISTS`，纯新增 | 1 次 | 1 次 |

严格物理单表若要干净落地，唯一路径是把 4 个战斗级字段折进现有 `room` 表 —— 但那要 **ALTER 老表加列**，正是 009950 事故（HTTP 500 / ws 1006）的高风险路径（v5 §0.5 第 2 条 / 坑 #17）；输入项 A §3 评估矩阵的「T6 三段式迁移模板」与 §8.6「优化补完轮不预建 `combat*` 表」均以「纯新增表、不动老表列」为前提。且 T6 已把 `schema.sql` 与 `room.js` 的 `TABLES` 合成单一源，多一张表不增加维护成本。

### I·3.6 排序与并列

- 排序键：**`value DESC` → `dex_mod DESC`（隐藏）→ `id ASC`**（先完成 `.ri` 的排在前面）。第三键用 `id ASC`：`INTEGER PRIMARY KEY` 自增、天然唯一且严格递增；批量独立掷骰会在同一毫秒建多行，`created_at` 相同，故不参与排序、仅作留痕/展示。
- **默认公式 = `d20 + 敏捷调整值`**：敏捷调整值从 `card_ref` 指向的卡读取，读得到用卡上值，无卡 / 卡上无数 / 他人 / 怪物 → 0；调整项按「基底在前、调整在后」拼在其后。
- **`dex_mod` 是与之同源同值的隐藏破平要素**：单独存字段，只用于 `value` 相同时的第二排序键，不对玩家显示、不重复计入 `value`；完整表达式 / 固定值路径下仍保留该快照。
- **同值不自动重骰**；不用幸运骰；无 `tie_break`、无 `.init first`。
- `.init set` 覆盖 `value`、`.ri` 同名覆写后 **`id` 与 `created_at` 均保持不变**（先入者优先，同值排序不跳位）；`dex_mod` 沿用条目 `card_ref` 的已存快照，不因改值重取。
- **改值 / 新增引发的顺位变化按 §3.4.3 处理**：`cursor_entry_id` 保持不变（指针跟着条目走、不会指错人）、`round` 不因改值变化、反馈带顺位影响提示 + 完整序列 + 指针；不做自动补正、不加 `acted` 字段。

### I·3.7 呈现

**已定：取消独立前端面板与 `INIT` 帧，先攻状态完全走消息流。**

- 理由：每条 `.init` 系列命令后已返回完整序列 + 指针，消息经 `BATCH` 帧广播，全房天然同步；刷新后靠首屏 200 条可回看。反馈里给完整序列 + 顺位提示、由玩家自行留意，消息流承载的信息已经足够。
- 收益：**零前端改动、零新 kind、零新帧**；E1 的 `frame-route` 注册不构成必须项（§0.2 的 E1 条件仅在「帧若存在」时适用）；E2 的协议守恒断言无需为新 kind 让步。
- 代价：没有常驻视觉锚点，玩家需发 `.init` 或翻消息才能看当前顺序 —— 已接受。
- 后续升级路径（当前不做）：若将来真机反馈「翻消息太麻烦」，再评估顶部细条 + `INIT` 瞬时帧，届时须按 §0.2 E1 登记 `OUT` 路由表，并同步 T3a/T4a 断言。

### I·3.8 老房间升级与清理/重置机制配合

> 设计约束：双表模式必须与消息清理机制及房间重置机制配合，不得导致其他机制失效；此为设计与测试重点。

#### 3.8.1 老房间升级

`room.js:109` 构造函数已执行 `TABLES.forEach(s => this.sql.exec(s))`，新表写成 `CREATE TABLE IF NOT EXISTS` 对**已存在的旧房间是纯新增**，DO 休眠唤醒时自然长出两张空表；不 ALTER 老表列、不重建表（重建 = 数据清空）。这正是输入项 A §3 评估矩阵「T6 三段式迁移模板」与 §8.6「不预建功能开发轮专用表」所划定的安全路径。

必须遵守三条既有契约：

1. **三段式顺序**（E3 / 009950）：`TABLES` → `ALTER`（幂等 try/catch）→ `INDEXES` 单独建。`room.js:70–86` 记录了事故：索引混进 `SCHEMA` 会让旧房间 DO 构造函数崩（HTTP 500 / ws 1006）。T6 已把该顺序做成可执行断言（输入项 A §7.2-④）。
2. **三份 storage 同步**：`room.js` / `tests/sqlite_storage.mjs` / `tests/memory_storage.mjs` 逐方法对齐，`check-worker.mjs` 会抓漏；`schema.sql` 与 `room.js` 的 `TABLES` 副本由 T6 合成单一源，T1 已补列级 DDL 一致性断言（起因正是 `room.notified_clean` 漂移）。
3. **两张表都要进「清空辅助表」清单**（见下）。

#### 3.8.2 与消息清理 / 房间重置配合的五条必守断言

| # | 风险 | 必须锁住的断言 / 测试 |
|---|---|---|
| **C1** | **清理判据被污染**：若把 `combat*` 的行数算进「是否仍有可清除信息」或「房间是否存活」，一个打完但没清表的空房间会**永远不重置** —— 与 §8.5 坑 5（`last_active` 被 alarm 自己续写）是**完全同型**的事故 | 静态断言：`alarm()` / 还原判定 / `reset_at` 计算**只读 `messages` + `idempotency`，不得读 `combat` / `combat_entry`**；构造「有先攻表但 messages 全过期」的房间跑一次 alarm，必须正常归零 |
| **C2** | **漏清一张表**：归零时只删 `messages` / `members` / `pcs` 而漏了 `combat` 或 `combat_entry`，还原后仍残留战斗状态，违反 B3 | 归零清空 SQL **必须同时覆盖两张表**，顺序先 `combat_entry` 后 `combat`（避免 `cursor_entry_id` 悬空）；断言：归零后两表 `COUNT(*)` 均为 0；T6b 四条守恒断言继续绿 |
| **C3** | **重置路径发广播**：归零清表时顺手发一条「战斗结束」显著广播，等于 `insertMsgs()` 写 `ts=now` 的新消息 → 计时主体自续到永不到期（§8.5 坑 1/2） | **重置路径静默清表，零消息、零 `allocSeq()`、零广播**（§3.2 的唯一例外）。断言：重置路径不得调用 `insertMsgs()` / 不得产生新 seq；广播只在**用户指令路径**触发 |
| **C4** | **战斗中掉表**：把辅助表挂到逐条消息到期 DELETE 的级联里，打到一半条目会消失 | 逐条 DELETE（滚动清理）**不动**任何辅助表；只有「由非空变空」那一次归零才清（L2 / L7）。测试：造一个 messages 部分过期、战斗进行中的房间 → 跑 alarm → 先攻条目数不变 |
| **C5** | **导入战报重建状态**：导入历史消息若被当成指令回放，会凭空开启战斗 | `planImport()` 只处理 `messages`，不执行 `handleCommand`，天然不会重建 `combat*`；仍写一条断言锁住「导入后 `combat` / `combat_entry` 行数不变」 |

> 这五条与输入项 A §7.2 的 ⑤⑥⑦⑧ 是同一组守恒断言的**扩展**：⑤ 墓碑守恒、⑥ 提醒非消息、⑦ 锚点隔离、⑧ 还原规格，加本文 C1–C5，共同构成功能开发轮验收闸门。

#### 3.8.3 双表特有的完整性风险

- `cursor_entry_id` 指向 `combat_entry.id`：删条目时若删的正是当前指针 → 指向排序下一位（§3.2）；清空时两表必须成对删除（C2）。
- 战斗开启广播只在 `combat` 行从无到有时发一次；`round` / `cursor` 变更不产生新 `combat` 行，避免重复广播。
- 先攻消息落 `messages` 参与续期（§3.3）：**战斗中房间持续存活是允许的**（用户主动动作）；但「先攻表存在」本身不续活（C1）。

#### 3.8.4 验证项

- 造一个只有 5 张旧表、含真实消息 / 角色卡 / PIN 的 DO → 唤醒 → 确认两张新表存在且为空，老数据完好。
- 旧 schema 房间跑一次 alarm 不中断（输入项 A T1 已列为验收项）。
- **C1–C5 五条各自「先红后绿」**：临时把 `combat_entry` 塞进清理判据 → C1 红；临时漏掉 `combat` 表的 DELETE → C2 红；临时在重置路径加一条广播 → C3 红；依此类推。
- 真机：老房间链接进房 → 发 `.ri` → 表可用；切规则 → 错配提示；`.init clear` / `.init combat end` → 战斗结束广播；切回 DND → 恢复可用。

### I·3.9 验收标准

1. `generic` / `coc7` / `dh` / `fu` 下发 `.ri` → 明确提示「这是 D&D 5e / 5.5e 规则下指令」，**不静默**、不落条目；`dnd5e` / `dnd5r` 下均可用。
2. 空表 `.init` → 「当前未开启」；首个 `.ri` → `⚔️ 先攻已开启`；表变空 → 「战斗结束，先攻表已清理」。清空类命令只发一条显著广播，不附完整序列与指针。
3. **广播统一不变量**：任何「空↔非空」状态变化的指令都给显著广播；表内增删、覆写、改值不改变空/非空状态的不广播；重置路径静默（C3）。
4. **表仍非空时** `.init` 系列每条后返回完整序列 + 指针；`.ri` 系列回「已添加 老王 17」／「已更新 老王 17 → 21」简短成功消息，**战斗进行中另带顺位影响提示 + 完整序列 + 指针**（§3.4.3）；战斗未开启的首个条目回一条 `notice` 简短消息 + 一条 `sys` 开启广播（两条用途不同，不算双发）；查看类落消息。
5. `.init <词>`（词 ∈ `end/finish/over/结束/next/下一位`）推进指针、**不清空表**；`.init combat <词>`（词 ∈ `end/finish/over`，**`next` 与中文 `结束` 均已删除**）与 **`.init 战斗结束`** 结束整场战斗并清空表；`.init clear` 清空表。`combat end` 不被 `end` 抢走，`战斗结束` 不被 `结束` 抢走（整串精确匹配断言）；`.init combat 结束` 应为**不合法指令**并给用法提示。
6. 错配状态下：仅 `clear`、`combat <词>` 与中文整串 `战斗结束` 放行，其余全部返回错配提示；切回 DND 自然恢复可用；表始终不清空。
7. 全部先攻指令与反馈落 `messages`，`ts=now`，导出 Markdown 战报可读，参与续期。
8. 排序：`value DESC, dex_mod DESC, id ASC`；`dex_mod` 不显示、只作破平第二键；**默认公式 = `d20 + 敏捷调整值`**，敏捷从卡读取、无卡 / 卡上无数 / 他人 / 怪物取 0；`dex_mod` 与默认公式里的敏捷调整值同源同值但**不重复计入 `value`**；完整表达式与固定值路径仍保留该快照；同值不自动重骰；无 `.init first`、无 `tie_break`。
9. 无 HP 字段、无逐骰明细、无 `expr` 字段、无阵营/权限字段、**无 `acted` 字段**、无归档表。
10. **upsert / 安全编辑分工**：`.ri`（三段标记）按 `name` upsert —— 存在则覆写并标记旧值→新值、不存在则新建；`.init set <名> <值>` 只编辑已有条目，名字不存在时明确报错、不创建、不触发开启广播；`.ri` 侧无 `.ri set/add/添加` 这类不掷骰的专门子命令。
11. `.ri d20+d8` 直接可用（无需 `=`）；`.ri +2` 叠加成 `d20 + 敏捷调整值 + 2`（敏捷取 0 时为 `d20+2`）；**`=d20+3 +2` 合并成 `d20+3+2`（1d20+5），不报错**；有卡且敏捷非 0 时 `.ri d20+2`（完整表达式）与 `.ri +2`（调整项）结果不同；`-1d4` 等负骰组显式报错；固定值 `18` 与表达式同现显式报错；`.ri 18` 固定值不掷骰；`.ri +1d4 adv 张三` ≡ `.ri 张三 adv +1d4`；`3#哥布林` 建 3 行且各自独立掷骰；**负敏捷调整值须符号规范化**——`dexMod = −1` 时默认公式拼成 `d20-1`（`parseExpr` 正常，mod = −1），不得拼成 `d20+-1`（实测 `syntax` 失败），`d20-1+2` → mod = +1。
12. **改值 / 新增影响顺位**：`.init set`、`.ri` 同名覆写、以及**战斗进行中的 `.ri` 新建**，反馈都带顺位影响提示 + 完整序列 + 指针；`cursor_entry_id` / `id` / `created_at` / `round` 均不变，不做自动补正、不做本轮指针调整。新增条目若排在指针之后按正常顺序推进即可；若插入已行动区域（指针之前），可能本轮被跳过——由玩家看完整序列自行独立判断并按需改值修正。战斗未开启的首个 `.ri` 无顺位问题，不带该提示。
13. **别名词表**：`.先攻`→`ri`、`.先攻表`→`init`、`.理智`→`sc`、`.死豁`/`.死亡豁免`→`ds`；`detectConflicts('verb', …)` 返回 `[]`；`.先攻表` 长优先于 `.先攻`（含 `.先攻表哥` 被 `init` 抢走的边角断言）；`.rc 理智` 不受 `.理智` 影响。
14. 老房间唤醒后功能完整；**C1–C5 五条断言全绿**；房间归零时两张表一并清空且满足 E5 / T6b 四条守恒。
15. 基线 E6 一条不降；不新增消息 kind、不新增 `INIT` 帧（已定取消面板与帧）。
16. **指针 / 回合 / 回退边界**：删除当前指针条目后指针指向排序下一位，删到空表给结束广播；推进走完一圈 `round` +1；`.init prev` / `.回退` / `.上一位` 到首位停、不倒扣 `round`。战斗进行中新增条目不改 `cursor_entry_id` / `round`，反馈带顺位影响提示 + 完整序列 + 指针，由玩家自行独立判断（不做自动补正）。

### I·4.1 `.sc`（COC 专属）—— 自动取卡上 SAN 的 `.rc 理智`

**最终口径**：`.sc` / `.理智` **完全等价于** `.rc 理智`（也可写 `.rc san` / `.sanity` / `.理智值`），即：

- **自动读卡上已录入的 `san` 字段值作为目标值**，`1d100` 对之判定，沿用现有五级成功等级。
- **只掷不改卡、不做 SAN 值追踪、不扣 SAN**。
- **「自动取」的准确边界（实测）**：是**读卡上已有的 `san` 字段**，**不是**从 POW 现场推导 SAN —— 后者是 `cocDerived()` 给出「复制一次 `.st set` 完成初始录入」的另一条链路。若玩家没做过那次录入、卡上没有 `san`，`.rc 理智` 现返回「卡上还没有「san」的数值 —— 用 `.st set san 60` 添加，或直接 `.r 1d100` 裸掷」；**`.sc` 继承同款提示，不自动算、不自动写卡**。这与「派生值不存副本」「车卡让玩家自己手动来」一致。
- **中文别名 `.理智`**：只收这一个，不收 `.理智检定` 等更长形式。

**★ 别名域结论（实测）**：`check:coc7` 与 `cardkey:coc7` 域里已注册 `理智 / 理智值 / san / sanity → san`（`lookupAlias` 返回 `{"key":"san","kind":"cocskill","display":"san"}`），所以 **`.rc 理智` 本来就是合法参数**，`.sc` 的等价关系完全站得住。`.rc 理智` 里的「理智」是**参数域**、`lookupAlias('check:coc7', …)`；`.理智` 是 **verb 域**，两域独立互不干扰。

**★ 中文动词别名的误切防护（实测）**：`isCommandText('。理智')` / `parseCommand('。理智')` / `'我们。理智还没恢复'` / 中文句号开头的 `.先攻表` 均返回 `false` / `null` —— 中文动词别名要求 ASCII `.` 开头，中文句号不会触发指令，无需额外防护。

**提示落点（已定）**：

| 落点 | 内容 | 代码位置 |
|---|---|---|
| `.help coc` | **相对完整**的一段：`.sc` / `.理智` 等价于自动取卡上 SAN 的 `.rc 理智`（`.rc san` 亦可）；**本版只掷不改卡**（与海豹/Dice! 不同）；成功等级沿用五级判定；卡上无 `san` 时提示先 `.st set san` 录入 | `help.js` `helpCoc()`（`94–139` 行） |
| `.rc list` | **一句提示**：`.sc / .理智 相当于 .rc 理智（自动取卡上 SAN）` | `pack_coc.js` 的 `listChecks()`（`.rc list` 内容由规则包提供，见 `cmd.js:365–366`；有卡时输出「属性 · 9 项 / 技能」两段，含 `san` 字样） |
| ~~`.st` / `.st list`~~ | **不加提示** | `.st list` 实际不存在；`cmd.js:288` 那个分支只是「查看当前卡 / 无卡时输出模板」 |

**与竞品的差异**：海豹 / Dice! 的 `.sc` 会**自动改卡**并联动 `.ti` / `.li` 疯狂症状；本项目版是纯检定，属刻意裁剪，与 S2 边界「不做动态资源追踪」自洽。风险是熟悉海豹的用户会预期自动扣 SAN，故 `.help coc` 要写完整。

### I·4.2 `.ds`（DND 专属）—— 带规则文字的 D20 检定

**最终口径**：`.ds` / `.死亡豁免` / **`.死豁`** = **带规则文字提示的 D20 检定**。实质 `.r 1d20` + 固定提示：

```
≥ 10 记一次成功　·　< 10 记一次失败　·　自然 1 计两次失败　·　自然 20 可回复 1 HP
```

- **不记数、不改 HP、不判断 3 次结果、不要求 hp=0 前置、不做 `.ds stat`、不自动折算昏迷伤害**。
- 中文别名 `.死亡豁免` / `.死豁` 与 `.ds` 等价，按现有 verb 域别名方式注册；实测 `detectConflicts()` 无冲突，两者同为 2 字以上中文动词、符合最长前缀匹配约束。
- 规则文字只是**提示**，骰娘不据此改变任何持久状态。

**与竞品的差异**：竞品的 `.ds` 价值主要在那套 3 次成功 / 3 次失败的计数状态机；去掉计数后增量价值接近 0，保留 B 方案 —— 保留一个「有规则语义的便利指令名」，成本极低。

### I·4.3 排期

`.sc` / `.ds` **不属于先攻与属性生成两个模块**，排在开发顺序第三位（先攻 → 属性生成 → 其他命令增补）。牌堆 / `.jrrp` / 变量宏 / 高级表达式等按 S2 边界声明不做，不排期。

## 附录 J · 部署链与预览路径现行口径（提炼自 v9 J·1–J·17）

> 本附录是 v9 附录 J（部署与预览路径逐步实测口径，含 J·17 交接增量）的**提炼替代**。逐步实测流水账已移除；保留的是**S2 开发仍要用的现行配置、判据与流程**。完整网页端操作见 `docs/用户手册.md` 第一节。

### J·1 Cloudflare Worker Previews · 四层配置模型（★ 最有价值的沉淀）

| 层 | 内容 | 坑 |
|---|---|---|
| ① 账户级资源 | KV / DO namespace 等 | 删资源 ≠ 删引用 |
| ② 生产绑定 | `wrangler.toml` 顶层 `[[durable_objects.bindings]]` | **顶级配置一条不动** |
| ③ Previews Base / 模板 | `[previews]` 块，影响**新建** Preview | 空块 → 缺 `ROOM` → 建房 500（#36） |
| ④ **已存在的 Preview 对象快照** | 该对象保存着绑定快照，**改 Base 不影响它**（官方口径） | 残留 KV 绑定 → 10041（#35）；排查要连这一层一起清 |

- 预览命令字段（Settings → Build）默认 `npx wrangler preview`（open beta），**硬性要求配置存在 `previews` 块**（#34）。
- **「运行时绑定」不继承生产设置**：凡代码通过 `env.X` 读取的，都要在 `[previews]` 里再声明一次。`index.js` 的 `env.ROOM.idFromName(code)` 属于此类 → `[[previews.durable_objects.bindings]]` 必须写 `ROOM` / `RoomDO`。
- `PIN_SECRET` 生产与每个 Preview **各有独立槽位**（#37），新开预览实例要单独补一次；**绝不轮换**。
- `[previews]` **只影响预览构建**；`wrangler deploy`（生产 `main`）行为不变。Cloudflare 为每个 Preview 自动 provision 独立 DO namespace，**预览房间数据与生产完全隔离**。

### J·2 现行 `wrangler.toml` 关键片段

```toml
# 顶层：assets / compatibility_date / durable_objects / main / migrations / name / observability 全部原样，一条不动
# 末尾（T1 新增，只影响预览）：
[previews]
[[previews.durable_objects.bindings]]
name = "ROOM"
class_name = "RoomDO"
```

> ★ 密钥只在 Cloudflare 网页端设置，**从不写进本文件**。★ 空 `previews` 块会让预览实例拿到 `env.ROOM === undefined` → `POST /api/room` 抛异常 → HTTP 500。

### J·3 判据订正（★ 别再用错）

- **`/vendor/protocol/index.js` 返回首页 200、不是 404**：`not_found_handling = "single-page-application"` 把找不到的静态资源路径兜成 `index.html` + 200；只有 `/api/*` 由 Worker 明确回 404。**判「生成物在不在」用本地 `build:web` 产物，不要用线上状态码**。
- **判通过看真实响应体，不靠日志数字**（`Read N files` 是枚举条目数，排除规则在其后才生效）。
- **点文件走 `Add file → Create new file` 手打含前导点的完整名**，并在 commit 变更列表里核对。
- **GitHub 把「删 ＋ 增」折叠成 rename** 是正常的：Git 树等价、单 commit、产物一致。
- **沙盒直连 `*.workers.dev` 会被 Cloudflare 403（`No policy rule matched`）**；判线上行为以「配置 ＋ 本地真跑 ＋ 用户在浏览器看到的真实响应」三方交叉为准。

### J·4 合并到 `main` 的影响评估（两种节奏共用）

| 查什么 | 结论 |
|---|---|
| `wrangler.toml` 顶级配置与迁移 tag | 原样 → DO 命名空间不变 |
| 房间定位 `env.ROOM.idFromName(code)` | 房间号不变、**已有房间数据不动、可访问性不变** |
| 幂等 DDL / 索引三段式 | `notified_clean` 用 `ALTER … ADD COLUMN` 只补列、不改已有行；索引必须在建表 ＋ 补列之后单独建（#17） |
| `PIN_SECRET` / preview 分支 | 未轮换、分支保留 |

**已知副作用**：部署瞬间**活跃 WebSocket 断开并自动重连** → 挑低活跃时段合并。
**生产复验必含**：真实旧房间号进房（如 593353），验历史消息、成员昵称、规则、战报条数；带 PIN 房间用**原 PIN** 能进。

### J·5 两种节奏（详见 §0.7 / 用户手册第一节）

- **节奏 A 标准**：一包 → preview 验 → 合并 `main` → 生产复验 → 下轮拉新代码比对再出包。大改动 / 封版步骤走这条。
- **节奏 B 开口「小步更新，打包同步」**：同一细分阶段、关联小改动、**起点两分支逐字节一致**、用户明确开启 → 几包累积在同一 preview、**每包仍各自验** → 最后一次性整合 `main`。开发侧锚点换 preview，并在「干净 `main` ＋ 各包叠加」上预演累积终态。实证：T6 家族三包。

### J·6 环境与复现（避免新对话踩沙盒坑）

- 工作目录 `/data/workspace`；拉仓库用 `curl -sSL https://codeload.github.com/Luffy852/ttrpg-dice-bot/zip/refs/heads/main`（**分支含斜杠时 zip 根目录名会变**，用 `namelist()[0]` 动态取，别硬编码）。
