# 部署指引：从「静态 index.html 推 Cloudflare」到「Worker + Durable Object」

> 适用对象：以前只用 GitHub 网页端上传 `index.html`、Cloudflare Pages 自动部署的同学。
> 这次**完全不是同一条路**，差异在第 0 节先讲清楚，避免按老经验操作。
> 日期：2026-10-29　对应代码：阶段 0 + 阶段 1（沙盒可验部分已收口）
> 配套：《测试项目清单.md》（部署后照着勾）

---

## 0. 先说清楚：这次和你以前做的有什么不一样

| | 你以前做的 | 这次 |
|---|---|---|
| 形态 | 一个 `index.html` 静态文件 | **一个 Worker（有后端）+ 前端静态资源** |
| 部署动作 | GitHub 网页端铅笔改文件 → Commit → 1 分钟生效 | **本地/命令行 `wrangler deploy`**，或 GitHub Actions 自动部署 |
| 仓库里是什么 | 就是那个 html | **几十个源码文件**；仓库 ≠ 线上产物 |
| 有没有服务器 | 没有，纯浏览器 | **有**：Cloudflare Worker + Durable Object（每房间一个） |
| 改一个字 | 网页端改完提交就行 | 改源码 → 提交 → Actions 跑测试 → 自动部署（或直接本地 deploy） |
| 数据存储 | 无（或 localStorage） | **Durable Object 内置 SQLite**，按房间存消息 |
| 需要密钥吗 | 不需要 | **需要**：`PIN_SECRET`（房间口令的签名密钥） |

一句话：**以前是"传文件"，现在是"发布一个带后端的应用"。**

### 0.1 你需要准备什么

- [ ] Cloudflare 账号（已有）
- [ ] GitHub 账号（已有）
- [ ] 本机装 Node 20+ 和 `npm`（命令行里 `node -v` 看一下）
- [ ] 一个 Cloudflare API Token（下面第 2 节一步步讲怎么拿）

## 2. 拿 Cloudflare API Token（一次性）

1. 打开 https://dash.cloudflare.com/profile/api-tokens
2. **Create Token** → 找到 **Edit Cloudflare Workers** 模板 → Use template
3. Account Resources：选你的账号
4. Zone Resources：先保持默认（我们暂不用自定义域名，用 `*.workers.dev`）
5. Continue to summary → Create Token
6. **复制那串 token**（只显示一次）

再拿 Account ID：Cloudflare 首页右侧栏或 Workers 概览页能看到，一串 32 位十六进制。

---

## 3. 把密钥放进 GitHub Secrets（**不要进仓库**）

仓库页面 → **Settings → Secrets and variables → Actions → New repository secret**，建两个：

| Name | Value |
|---|---|
| `CLOUDFLARE_API_TOKEN` | 第 2 步那串 token |
| `CLOUDFLARE_ACCOUNT_ID` | 你的 Account ID |

**`PIN_SECRET` 不在这里建** —— 它由下面的命令行设置，值不进仓库（见 4.2）。

## 4. 部署（两条路，选一条）

### 4.1 路线 A：GitHub Actions 自动部署（推荐，长期用）

推代码到 `main` 就会触发 `.github/workflows/deploy.yml`：
先跑测试（引擎双路 676×2 + 协议 51 + schema 27 + worker 42 + 端到端冒烟），全绿才部署。

> ⚠️ **当前 workflow 里 `secrets: | PIN_SECRET` 这一行需要你先在仓库里建同名 Secret**，
> 或者改用 4.2 的命令行方式设一次（推荐后者 —— 口令密钥不该经过 GitHub）。

### 4.2 路线 B：本机命令行部署（第一次建议用这条，看得见报错）

```bash
cd /data/workspace/ttrpg-dice-bot
npm i                                    # 装依赖（jsdom / sql.js 等，只本地用）
npm run check:all                        # 先本地验一遍：拆包自检 + 全部测试 + 变异 + 快照

cd apps/worker
npx wrangler login                       # 第一次会开浏览器让你授权
npx wrangler secret put PIN_SECRET       # 交互式输入一个长随机串（记下来，丢了旧房间口令会失效）
npx wrangler deploy                      # 部署
```

`PIN_SECRET` 生成一个（任选其一）：
```bash
openssl rand -base64 32          # mac/linux
# 或 node -e "console.log(require('crypto').randomBytes(24).toString('base64'))"
```

部署成功后会给你一个地址，形如：
```
https://ttrpg-dice-bot.<你的子域>.workers.dev
```

## 5. 首次部署后必做的 3 个检查

```bash
# ① 服务活着吗（应返回 JSON）
curl https://ttrpg-dice-bot.<你的子域>.workers.dev/api/room/000000/meta
#   → 期望：{"error":"no_room"} 或房间信息；**不应该是 Cloudflare 1101/错误页**

# ② 建一个房间
curl -X POST https://ttrpg-dice-bot.<你的子域>.workers.dev/api/room -d '{}'
#   → 期望：{"code":"123456","has_pin":false,"pin":null}

# ③ 看实时日志（另开一个终端挂着）
npx wrangler tail
```

第 ③ 步很有用：后面每次点页面，终端里都会打印请求与异常。
**部署后先挂着它，再打开页面操作**，哪里报错一眼看到。

## 6. 这次部署特有的三个坑（和静态站完全不同）

| 坑 | 表现 | 怎么办 |
|---|---|---|
| **DO 需要 migration** | 首次部署报 "Durable Object class not found / migration required" | `wrangler.toml` 里已写了 `[[migrations]] new_sqlite_classes=["RoomDO"]`。**部署后不要手改这段**，否则要新增一条新 tag 的 migration |
| **前端不是 Pages** | 打开页面 404 | 前端由 `[assets] directory = "apps/web"` 托管，必须在 `apps/worker` 目录下 deploy（不是仓库根） |
| **改了前端没生效** | 刷新还是老的 | 静态资源有 CDN 缓存；`wrangler deploy` 会刷新，极端情况用无痕窗口或加 `?v=` |

另外两条**已知的设计约束**，不是 bug：
- **房间号 6 位数字必然可枚举**（10⁶）—— 开放房间靠"号码不公开"，要防误入请勾 PIN
- **PIN 不可修改、不可找回** —— 创建时那一次展示是唯一一次，必须截图（房间号与口令分开显示就是这个原因）

## 7. 怎么盯占用（**只看本项目，不用管你另外两个小工具**）

Durable Object 天生隔离，**没有任何一处能直接看到"总共占了多少"** —— 这是架构特性不是配置问题。当前阶段用下面两个办法估：

1. **Dashboard**：Workers & Pages → 你的 Worker → Durable Objects → 能看到 DO 实例数与存储
2. **粗算**：单房间稳态 ≈ 1.5 MB（100 骰/天 × 30 天 × 300–800 B）；
   100 个活跃房间 ≈ **200–300 MB**。只要活跃房间数没上几百，离 500 MB 阈值还远

> 阶段 4 会加 KV 自报 + Cron 汇总，那时才有真正的全局视图。
> 30 天的清理是每个房间自己的 alarm 在跑，不需要你干预。

---

## 8. 出问题怎么回滚

- **回滚代码**：Cloudflare Dashboard → Workers → 你的 Worker → Deployments → 找到上一个 → **Rollback**
  也可以 `git revert` 后重新推（Actions 会自动部署）
- **房间数据不受影响**：消息存在 DO 的 SQLite 里，代码回滚不会清数据
- **彻底重来**：`npx wrangler delete` 会删整个 Worker 与所有房间数据（**慎用，不可恢复**）

## 9. 部署顺序建议（照这个走，出问题好定位）

1. `npm run check:all` 本地全绿
2. `wrangler deploy` 部署
3. `curl` 三个检查（第 5 节）
4. 浏览器打开 → **先只做一件事**：建房间 → 进去 → 发一条 `.r 2d6+3`
5. 这一条通了，再照《测试项目清单.md》逐条勾
6. 卡在哪一步就停在哪一步，把 `wrangler tail` 的输出发给我

**不要一次把所有功能都试完再来看结果** —— 那样出问题分不清是前端、协议还是部署。
